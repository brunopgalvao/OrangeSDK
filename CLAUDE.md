# Solo — Claude instructions

Solo is a framework for EVM-compatible solochains: a from-scratch RISC-V derived VM, a host binary shared by every chain, and a governance-upgradeable kernel that includes consensus. Working name; rename pending.

## Rules

- `spec/` is normative. Code that disagrees with the spec is a bug in the code, unless an ADR in the codex changes the spec first.
- Full test coverage is a gate, not a goal: CI fails under 100% line coverage. Every backend is differentially tested against the reference interpreter. Every change to a cost table has a test that pins the number.
- No `unsafe` outside crates whose name ends in `-jit` or `-sandbox`, and there only behind a documented invariant.
- Commit straight to `main`. Commit messages say why. Never mention AI assistance in commits, PRs, or code.
- Dates absolute, never relative.

## Layout

- `spec/` — the VM, module format, gas, host ABI, driver interface, reference consensus (08), transport (09), state commitment (10), telemetry (11), threshold certificates (12), kernel upgrades, feature gates and two-track governance (13), mempool (14), staking, epochs, slashing and the threshold key (15), kernel modules and native contracts (16), the bridge to Ethereum (17), the bridge from Ethereum (18), precompiles and kernel gas (19), the Ethereum surface (20: set-code transactions, Ethereum headers and roots, `eth_getProof`, historical state), the canonical token bridge (21) and storage and snapshots (22: the chain store on disk, restarts, the snapshot record and file) specifications.
- `crates/solo-vm` — reference interpreter, `no_std`-capable, the oracle for every other backend. `crates/solo-jit` — the native backend (AArch64, x86-64), differentially tested against it (spec 07 §4.1).
- `crates/solo-recompile` — RV64 ELF to Solo module. `crates/solo-host` — executor and host ABI. `crates/solo-abi` — codec and shared types. `crates/solo-eth` — Ethereum transactions (EIP-7702 included), the Ethereum header and receipt encodings and Merkle-Patricia roots (spec 20). `crates/solo-rlp` — RLP. `crates/solo-trie` — the binary Merkle trie of the state commitment (spec 10), with nodes loaded on demand from a `NodeSource`. `crates/solo-store` — the chain store on disk (spec 22): `DiskStore`, one `redb` file per node with the flat state, reference-counted trie nodes per kept root, the history window and the version log, sealed per block; and `snapshot`, the committee-signed snapshot file. `crates/solo-bls` — threshold BLS, DKG and resharing, finality certificates (spec 12). `crates/solo-upgrade` — kernel upgrade actions, their records and the feature-gate state machine (spec 13). `crates/solo-ethlc` — the Ethereum light client, message proofs and inbox logic of spec 18, shared by the kernel, its two bridge modules and host tests; `crates/solo-bridge` — the relayer library of the bridge to Ethereum (spec 17): light-client submissions from threshold certificates, key rotations from recorded handoffs, outbox proofs and contract calldata, and in `tokens` the token bridge's messages, wrapped-token addresses and calldata (spec 21).
- `crates/solo-node` — node host (driver loop, mempool (spec 14), queries, kernel switchover and gated host functions, the threshold keystore behind `sign` key role 2, the on-disk driver store of `store.rs` and the chain state of `state.rs`, in memory or in a `DiskStore`, both of which `--data-dir` opens; a node resumes from its store without executing again, and imports a snapshot) and `Sim`, the in-process multi-node network for consensus tests. `crates/solo-rpc` — Ethereum JSON-RPC (state at any height the node keeps, `eth_getProof` with spec 10 proofs), plus the bridge relayer's `solo_getFinalityProof`, `solo_getOutboxProof` and `solo_getRotation`, governance's `solo_getGovernance`, `solo_getProposals` and `solo_getProposal`, and `solo_upgradeStatus`. `crates/solo-cli` — the `solo` command: `dev`, `node`, `key`, `gov` (the encoder of governance calls, spec 13 §9), `doctor`, `upgrade` (stage and propose a kernel with the governance key), `snapshot` (`export`, `verify`, `import`; `solo node --snapshot` joins from one) and `devnet` (a network of validator processes on one machine: `init`, `up`, `down`, `stop`, `start`, `status`, `wait`, and `node` for one validator in-process with any `solo node` option); `tools/rehearse-upgrade.sh` rehearses an upgrade, a gate activation and a validator restart against it, and `crates/solo-cli/tests/devnet.rs` runs that on real processes.
- `crates/solo-conformance` — Ethereum execution-spec state tests through the recompiler and both backends (spec 07 §4.2); the committed subset and its expected failures live in its `tests/fixtures`.
- `guest/` — separate RISC-V workspace: `solo-guest` runtime, `hello`, the reference `kernel`, `solo-module`, the example module `modules/counter`, the bridge modules `modules/eth-light-client` and `modules/eth-message-verifier`, the precompile module `modules/precompiles` (spec 19), and `evm-conformance`, which includes the kernel's `evm.rs`, `native.rs`, `outbox.rs`, `modules.rs`, `precompiles.rs`, `state.rs` and `tx.rs` by path. Rebuild fixtures with `tools/build-guest.sh` after touching it; it builds the precompile module first and recompiles it into `guest/kernel/precompiles.solo`, which the kernel embeds, then `hello.elf`, `kernel.elf`, `counter.elf`, `eth-light-client.elf`, `eth-message-verifier.elf`, `evm-conformance.elf` and, with the `upgrade-test` feature, `kernel_v2.elf`, at one fixed staging path so the binaries do not depend on the checkout. The kernel embeds `contracts/build/EthereumInbox.bin-runtime`.
- `contracts/` — the bridges' Solidity contracts and their compiled fixtures in `contracts/build` (with `SOURCES`, the sha256 of every source): deployed on Ethereum, `SoloFinalityVerifierV2` and `SoloLightClientV2` (rotating keys), `SoloFinalityVerifierV1` and `SoloLightClient` (a fixed key), `SoloInbox` (spec 17) and `EthereumOutbox` (spec 18); deployed on Solo, `EthereumInbox` (spec 18); in `contracts/tokens`, the token gateways `TokenGatewayOnEthereum` and `TokenGatewayOnSolo` and the wrapped `BridgedToken` (spec 21). `tools/build-contracts.sh` rebuilds them all with solc 0.8.28.
- `tools/` — build scripts; `fetch-conformance.sh` and `curate-conformance.py` for the execution-spec fixtures; differential fuzz harnesses as they land.
- `crates/solo-metrics` and `ops/` — telemetry (spec 11) and the alert rules and dashboard over it; a test keeps `ops/` and the spec's metric table in step with what the node exports. `ops/Dockerfile` and `ops/docker-compose.yml` run the four-validator devnet as containers with Prometheus and Grafana (`ops/README.md`); `tools/compose-rehearsal.sh` rehearses the upgrade on it when `SOLO_DOCKER` is set.
