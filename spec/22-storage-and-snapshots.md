# 22 — Storage and snapshots (version 0)

## 1. Overview

A node keeps its chain state across restarts. This document specifies what the reference host writes to disk under its data directory, when, and with what atomicity (§2–§4); what a restarted node does with it (§5); the snapshot record the kernel writes at every epoch boundary (§6); the snapshot file a node exports from that record, how a new node verifies one before it serves anything, how it joins the chain from it, and how it fetches one from its peers (§7); what bounds the disk, how long the driver's tables are kept, and what telemetry reports (§8). Codex ADR 0037 records the decisions; codex ADR 0039 the authenticated head, the streamed file and the retention of the driver's tables.

Two stores sit side by side in the data directory. The *driver store* (spec 08 §7, codex ADR 0036: `driver.state` and `persist.log`) holds what the driver persists through `persist_*` and `PersistState`: node-local, synced before anything the node signs leaves it. The *chain store* (`chain.redb`, this document) holds the chain state the kernel reads and writes through the storage functions of spec 05 §4.2, the trie behind every header root the node still serves, the history window of spec 20 §5 and the block log of §5. The in-memory state of `solo dev` without `--data-dir` and of the simulator keeps the same contents in memory; everything observable (roots, proofs, queries at a height) is the same from either.

## 2. Contents

The chain store holds, for one chain:

| What | Keyed by | Content |
|---|---|---|
| the flat state | the stored key (10 §2) | its value, keys under `local/` included |
| trie nodes | node hash | the 65-byte preimage of spec 10 §4 and a reference count: how many live parents and roots name the node |
| history | `(key, version)` | what the key held before the span of `version` first wrote it: absent, or the value |
| writes | `(version, key)` | the keys each version's span wrote, to prune by |
| versions | version | the header root the version's trie is kept for (for version 0 the genesis header's, 20 §3.4, or the state's own root under a kernel that stores no genesis block; none when the kernel asked for no root in that block, and none for a version loaded from a snapshot), the number of keys its span wrote, and the number of committed entries it holds |
| metadata | name | the latest and oldest versions kept, the root of the current trie, the code hash of the kernel that wrote last, the genesis root, the format |

A *version* is a sealed block height: the genesis state is version 0, and each executed block seals its height. The *span* of version `v` is everything written since version `v − 1` was sealed: the block's execution, the finalization and kernel-switch writes before it, and nothing after it. History and tries keep the semantics of spec 20 §5.1: reading as version `v` yields the committed entries as they were when `v` was sealed, and the trie of `v` is the one behind the root of block `v`'s header, which the kernel asked for before its bookkeeping writes (06 §5).

Receipts, transactions and block headers are chain state (`receipt/`, `txraw/`, `block/`, `bnum/`, `bhash/`, spec 20 §3) and live in the flat state like every other key; the store adds nothing for them.

## 3. Trie nodes

### 3.1 Content addressing

Nodes are stored under their hash, so a node shared by many versions is stored once, and a trie is opened from its root alone: the host reads a node when a path first passes through it (an update or a proof), never the whole trie. A node opened over its store therefore starts in constant time whatever the size of the state, and the memory it uses grows with the paths it touches.

### 3.2 Reference counts

A node's count is the number of nodes among the kept tries that name it as a child, plus the roots that name it: one for each version whose header root it is, and one for the root of the current state. Sealing a version writes the nodes its span created, each counting one reference for every child it names, and one reference for the version's root and one for the current root, giving back the previous current root's reference. The nodes a span created all lie on the paths of the keys the span wrote, so the host writes them by walking those paths from the root and stopping at the first node whose row exists and was not written on that walk: its subtree is on disk and counted.

Pruning a version (§8) gives its root's reference back; a node whose count reaches zero is deleted and gives back the references it held. A node two versions share by hash keeps the count both gave it, so a write that restores an older value restores an older node without confusing the counts.

## 4. Atomicity

One transaction seals a version: the span's writes to the flat state, its history rows and write rows, the trie nodes it created with their counts, the version row and the metadata, committed together and synced to disk before the host goes on. A crash before the commit leaves the store exactly as the version before left it; a crash after it leaves the version whole. Nothing is ever torn.

Between seals the host buffers the kernel's writes in memory and reads through them, so a kernel call sees what the calls before it wrote whether or not a version has been sealed since. Two more transactions write the buffer without sealing: after `kernel_stf_finalize_block` (the finalized height, under `local/`) and after `kernel_migrate` (the switch record of spec 13 §5, with the code hash of the new kernel as the kernel that writes from then on). A crash between a block's seal and its finalization write loses the finalized height only, which §5 recovers.

The write of a block that fails (the disk refuses, or, in a test build, an injected fault drops the transaction: `Fault::DropNextCommit` exists only with the store's `fault-injection` feature, which the node's tests turn on and no release build has) halts the node: every later step reports the failure, nothing the failing step queued for peers is sent (its driver state never reached the driver store, so a restarted node could otherwise sign differently in a view it had signed in), the block is not on disk, and the driver's tables already say it was finalized, so the node restarts over the store, where §5 takes it up again. The reference implementation's engine is `redb` (codex ADR 0037): one file, copy-on-write B-trees, a commit that is durable when it returns.

## 5. Restarts

A node opened over a store that a previous run sealed runs no `kernel_init` and executes nothing again. It reads the metadata, opens the current trie from its root, and takes the store's latest version as its executed height and as a finalized height (the reference host executes finalized blocks only, 08 §5). It loads the kernel named on the command line; when the store names another kernel as the last writer, that kernel is an upgrade the chain enacted, whose code chain state holds (13 §6), and the node compiles and runs that one instead, with the gates active for the next block (13 §8.6); a store last written by a kernel that is neither is refused. It then does what it does after every executed block (13 §7.1): reads the upgrade status, prepares a pending upgrade, switches at the activation height if the store's head is that height, and reads the fee market (23 §7), so admission and the pool's take apply the head's next base fee before any block executes. The base fee of the synthetic genesis block (23 §7) is block 1's, which the genesis parameters alone set (23 §3).

The driver resumes from the driver store as before (08 §7). Its tables can lag the chain store: the chain store commits a block inside the step that executes it, the driver store syncs after the step. To close the gap without a peer, the reference driver keeps a *block log* in chain state, under `local/log/` (node-local, outside the commitment, 10 §2): for each height it finalizes, in the same step that asks for the block's execution and therefore in the block's transaction, the proposal (`local/log/prop/` + height), its finalize vote certificate (`local/log/cert/` + height) and its threshold certificate when it has one (`local/log/bcert/` + height), dropping the entries 64 heights behind. On `Started`, when chain state is ahead of the finalized height the driver remembers, the driver takes the heights between from the log into its tables (08 §7), makes the last one its tip when its tip is behind it, enters the view after that certificate's when its view is not past it (views only increase, 08 §3), and sets its finalized height to the chain state's. When chain state is behind, it replays its own finalized blocks as 08 §7 says, which with this store happens at most for the block whose write a crash cut short.

A node started over a store therefore resumes in constant time: the time to open the file and read a few rows, not a function of the chain's length, the versions it keeps or the state's size. The history window's bound in key writes (20 §5.1) is read from the version rows when a block is sealed, never held in memory per version. `solo node` and `solo dev` open the chain store under `--data-dir`; without it the state stays in memory. `solo_node_open_seconds` reports the time (§8.2).

## 6. The snapshot record

The reference kernel writes a *snapshot record* for every completed epoch. The epoch length is the staking epoch (15 §4) when staking is on; else the feature-gate epoch (13 §8) when upgrades are governed; else `SNAPSHOT_INTERVAL` = 1 024 blocks. In the first block of epoch `e + 1` (height `end(e) + 1`), before anything else of the block, the kernel asks for the state commitment (`storage_commit`): the root of the whole state as block `end(e)` left it, its bookkeeping included, which is exactly the state the host sealed as version `end(e)`. It stores

```
struct SnapshotRecord { height: u64, state_root: [32] }    // height = end(e)
```

under `snap/` + `e` (big-endian u64) and `e` under `meta/snapshot`. Both are committed keys: the record is in the root of block `end(e) + 1` and of every later block, so a certificate for any later proposal vouches for it through the proposal's anchor (17 §4) and a spec 10 proof of the key. The query `snapshot` takes an epoch (`u64`) or nothing, for the latest, and returns the record; status 1 when there is none yet.

A snapshot is *identified* by its record: the chain, the epoch, the height and the root. Two nodes export the same snapshot of an epoch whatever they did since.

## 7. Snapshot files

### 7.1 Export

`solo snapshot export --data-dir <dir> --out <file> [--epoch <n>]`, over a stopped node's directory, writes the snapshot of an epoch (the latest recorded by default). The file holds:

- a header: the chain id, the epoch, the record's height and root, the entry count; the encoded proposal `P` that vouches for the record, its certificate (a version-2 threshold certificate when the node stored one for `P`, 08 §6a, else `P`'s finalize vote certificate, 08 §6) and the spec 10 proof of `snap/` + epoch against `P.anchor_root`; the proposal of block `height`, its finalize vote certificate and its threshold certificate when there is one, for the importing node's driver; and the *links*: the encoded finalized proposals of the heights `height + 1` to `P.height − 1`, lowest first, through which `P` vouches for the head (§7.2, check 6);
- the committed entries of version `height`, keys under `local/` left out, each as `key length ‖ key ‖ value length ‖ value` with `u32` little-endian lengths, in strictly ascending order of their paths, `keccak256(key)` (10 §3).

The file starts with `SOLOSNAP`, the format (`u32`, 2) and the header's length (`u32`) before the header; a file of format 1 (entries in key order, no links) is refused. `P` is a finalized proposal in the node's tables whose `anchor_height` is above the record's height, whose view is at or above the head certificate's (§7.2, check 6) and whose anchor root the store still keeps the trie of (the record is written in block `height + 1`, so a proposal anchoring `height + 1` or later covers it), and that has a certificate. Of these the exporter takes the lowest whose certificate needs the trust the latest one's needs (a threshold certificate of the same key set, or a vote certificate), so that the links are as few as the trust a verifier holds allows; without one, or when the window no longer reaches `height`, or when the tables lack a proposal between, the export fails and says so. It also fails, naming the cause, when the entries do not hash to the record's root: a kernel switch right after block `height` (13 §5) writes its switch record after the version is sealed and before the next block takes the record's root, so that epoch has no snapshot in version 0 and another epoch's serves.

The export streams: the store hands out the entries of version `height` in key order from the file, walking the state table and the history rows written after `height` side by side; the exporter puts them in path order with an external sort, in runs of at most `chunk_bytes` (64 MiB) of entries in memory, each sorted and written to a scratch directory beside the output, then merged `fan_in` (64) runs at a time, in as many passes as it takes, hashing the entries into the trie as the last merge writes them (the stack of pending subtrees of `solo_trie::SortedRoot`, at most one per path bit). Its memory is therefore bounded by `chunk_bytes`, the merge's read buffers and the header, whatever the size of the state; the output appears, renamed into place, only once whole and checked, and the scratch directory goes with the export.
### 7.2 Verification

`solo snapshot verify --snapshot <file> --genesis <genesis.json> [--trust-key <0x 96 bytes>]`, and every import, checks in order:

1. the chain id is the genesis file's;
2. `P` decodes and `P.anchor_height > height`;
3. the certificate is `P`'s and verifies under the trust: a threshold certificate (12 §7) must name `P`'s height and hash and verify, over the chain id and its key id, under the group key `--trust-key` names; a vote certificate must be a finalize certificate for `P`'s hash whose votes index the genesis validator set, with distinct indices, weighing a quorum (08 §1) and each recovering to its validator (08 §6), which is accepted only without `--trust-key` and only for a chain without staking: the genesis set is the chain's set for good only there, and on a chain with staking validators that have since left the set could sign a history of their own, so a verifier of such a chain refuses to go on without `--trust-key`;
4. the proof is a spec 10 proof of `snap/` + epoch against `P.anchor_root` whose outcome is *present* with the value hash of the encoded record `{ height, state_root }`;
5. the entries number what the header says (the file ends neither before the last nor after it), are committed keys in strictly ascending path order, and their trie (10 §4) hashes to `state_root`, computed as they stream from the file with `SortedRoot`, in memory bounded by the depth of the trie;
6. the head proposal decodes and is block `height`'s, and it is joined to `P` by the links: each link decodes, is one height above the proposal before it (the head for the first) and names that proposal's hash as its parent, and `P` is one height above the last (the head, without links) and names it as its parent. `P` is vouched for by check 3, and a proposal's hash covers its parent's, so the trust that vouches for `P` vouches for the head proposal: the importing driver's tip is the chain's. The head certificate is a finalize certificate whose view is not above `P`'s; it names the head or a descendant that finalized it, such as a suffix proposal (08 §3a), which is not in the file; under the genesis set its votes must also verify as in check 3. It seeds the importing driver's entry certificate and view, and bounding its view by `P`'s keeps a forged one from moving a node past the views the chain has had.

Anything else is refused with the first failing check named. The trusted group key is the verifier's own assumption: the key of the chain's current key set, as the light client on Ethereum holds it (17 §5) or a node the operator trusts reports it. A chain whose key has rotated past the one the operator trusts needs a newer snapshot or a newer key.

### 7.3 Import and joining

`solo snapshot import --snapshot <file> --data-dir <dir> --kernel <kernel> --genesis <genesis.json> [--trust-key …]` verifies the file and loads it into a data directory that holds no chain yet, and `solo node --data-dir <dir> --snapshot <file> [--trust-key …]` does the same before starting when the directory holds no chain (a directory that holds one keeps it and says the snapshot was ignored). Loading runs `kernel_init` first, so the store holds the genesis and its genesis block (20 §3.4), then, in one transaction, replaces the state with the entries as they stream from the file, writing each entry and the trie nodes it completes as it arrives (`SortedRoot` again, so the memory used is bounded by the trie's depth and the engine's page cache, not by the state), and commits only once the entries were in path order and hash to the record's root, and name at `bnum/` ‖ 0 the genesis hash the local `kernel_init` stored (none where it stored none): a snapshot of a chain with another genesis, whatever its chain id and certificates, is refused, as the chain identity of 20 §3.4 requires. A file that fails leaves the directory with the genesis alone; it seals version `height` as the oldest and latest version with no header root (proofs begin with the next block), writes the finalized height and the block log entry of `height` under `local/`, takes up the kernel the state's latest enacted upgrade names (13 §6), the genesis kernel when there is none, and reads the fee market at `height` as §5 does. The fee records are chain state (23 §6: the parameters, the reward pool, the stakes and delegations, the balances), so the snapshot carries them and the joined node prices the next block as the chain does. Queries answer at `height` and above; `eth_getProof` from `height + 1` on.

Started with no driver data, the driver finds chain state ahead of a finalized height of 0, takes block `height` from the log (§5), enters the view after its certificate's or, with staking, the first view of the next epoch (08 §3a), looks itself up in that epoch's set, and syncs forward from its peers from `height + 1` (08 §7a), finalizing and executing as any node does. A validator reinstalled this way is back in consensus once it has synced to the head; it has nothing of its old driver tables, so a key that had voted in the current view before the reinstall would vote again: operators reinstall a key only from a directory whose driver store they keep, or after a view has passed.

### 7.4 Fetching a snapshot from peers

A node can join from its peers instead of from a file: it fetches a snapshot over the transport (09 §6), verifies it as it arrives, assembles the file of §7.1 from it and imports that as §7.3 says. Codex ADR 0044 records the decisions.

**Serving.** `solo node --data-dir <dir> --serve-snapshots` keeps the snapshot of the latest recorded epoch as a file under `<dir>/snapshots/`, exported as §7.1 says, and answers requests for it. After every step that finalized a block, a node that serves and holds a record newer than the newest snapshot it serves exports that record's snapshot; when the export fails (no certified proposal anchors a kept height above the record yet, the usual case for the first blocks of an epoch), it tries again after the next finalized block, which is cheap because the export looks for the certificate before it sorts the entries. It serves the files of the `SERVED` = 2 latest epochs and deletes older ones, and on restart serves what the directory holds. For each file it serves it computes, in one pass over the entries, the *manifest*: the entries split by the first `depth` bits of their paths into `2^depth` *slices*, `depth` the smallest at which the entries number at most `SLICE_ENTRIES` (4 096) times `2^depth`, at most `MAX_DEPTH` (16); and, for each slice, a summary of its subtree: `Empty` when no entry falls in it, `Leaf { path, value_hash }` for one entry, `Branch { hash }` with the subtree hash `T(S, depth)` of spec 10 §4 for two or more. It keeps each slice's offset in the file, so that a request reads only its slice. These limits are the server's choice (the reference server takes others in tests): a joining node accepts any `depth` up to `MAX_DEPTH` and any page of at least one entry.

**Exporting in the background.** A node that runs its heavy work off the loop that steps its driver (`NodeConfig::background`; `solo node` and `solo dev` do) exports in two halves (codex ADR 0046). In the step, it finds the record, the head and what vouches for them as above, which is cheap, and *freezes* the chain store: it opens a read transaction of its own over what is committed and copies what is buffered above it, so that the blocks the node executes, seals and prunes afterwards do not change what the export reads. A worker thread then walks the frozen state's entries at the record's height, sorts them and writes the file, while the node goes on executing and voting. One export runs at a time; the node serves the file from the first step after the worker ends, and when the export failed it tries again after the next finalized block. A node that stops calls a running export off: the worker stops at its next entry and removes its scratch, leaving no file. While the export runs, the engine keeps every page the frozen transaction reads, so the file can grow by what the blocks meanwhile free, and a compaction waits until it ends. A node without the background exports in its step and pauses for as long as the export takes; the simulator's nodes do, which keeps every run of a simulated network the same.

**Messages.** The payloads of `SyncRequest` and `SyncResponse` (09 §2) are, in the canonical encoding (06 §2):

```
enum SyncRequest {
  0 Offers
  1 Manifest { epoch: u64 }
  2 Slice    { epoch: u64, slice: u32, after: Option<[32]> }
}
enum SyncResponse {
  0 Offers      { offers: vec<Offer> }                    // newest first
  1 Manifest    { header: bytes, depth: u8, slices: vec<Summary> }
  2 Slice       { entries: vec<Entry>, more: bool }
  3 Unavailable                                            // the epoch is not served (any more)
}
struct Offer { epoch: u64, height: u64, state_root: [32], entries: u64 }
enum Summary { 0 Empty, 1 Leaf { path: [32], value_hash: [32] }, 2 Branch { hash: [32] } }
struct Entry { key: bytes, value: bytes }
```

`Manifest` answers with the snapshot's header (§7.1, encoded) and its manifest. `Slice` answers with the entries of slice `slice` whose paths are above `after` (all of them for `None`), in path order, as many as fit in `CHUNK_BYTES` (1 MiB) of keys and values, at least one, and `more` saying whether entries of the slice follow. A node that does not serve the epoch answers `Unavailable`; a node that serves nothing answers `Offers` with none.

**Fetching.** `solo node --data-dir <dir> --sync-from-peers [--trust-key …]`, when the directory holds no chain, opens it (running `kernel_init`, so that it holds the genesis and its genesis block), connects to its `--peer` addresses and, before the driver starts:

1. *Discovery.* It asks every peer it handshakes with for its offers. Once every connected peer has answered, or `OFFER_WAIT_MS` (1 000 ms) after the first answer, it takes as its *target* the newest epoch any peer offers, and of the offers of that epoch the `(height, state_root)` the most peers name. Peers that connect later are asked too, and become sources when they offer the target. While no peer offers anything, as when the node starts before its peers have exported a snapshot, each peer is asked again `OFFER_WAIT_MS` after its last answer; whenever discovery chooses again, every peer is asked again.
2. *Manifest.* It asks one peer that offers the target for the manifest, and accepts it only when: the header names the target's chain id, epoch, height and root; the header verifies under the node's trust as §7.2 checks 1 to 4 and 6 say (the entries are checked as they arrive instead of check 5); `depth` is at most `MAX_DEPTH` and there are `2^depth` summaries; each `Leaf`'s path begins with its slice's bits; and the summaries combine to the record's root. They combine level by level from `depth` up to 0: two `Empty` halves make an `Empty`; an `Empty` and a `Leaf`, either way round, make that `Leaf`, which spec 10 §4 places as high as possible; anything else makes `Branch { branch(h₀, h₁) }`, where `h` is `EMPTY` for an `Empty`, `leaf(path, value_hash)` for a `Leaf` and `hash` for a `Branch`. The root is the hash of the summary left at depth 0. A leaf's path in its summary binds it to its slice, so that a manifest that combines to the root says exactly which slices are empty and what each other slice's subtree is: honest entries never fail against an accepted manifest, and a slice that fails is the fault of the peer that sent it. A manifest that is refused is the sender's fault, and discovery chooses again without it, with one exception. A manifest whose header passes every check but the last of check 3, its threshold certificate being well formed and the anchoring proposal's but not verifying under the trusted group key, may be honest: the snapshot's certificate is the key set's that certified the chain when it was exported, and the key the node trusts, the chain's current one, may have been handed off to since (15 §6.6), so that the next epoch's snapshot verifies. Such an offer is *set aside*: discovery never takes it again in this sync, from any peer. The peer is not banned for its first such manifest, and is for its second. A peer every one of whose latest offers is set aside no longer counts for 09 §6, so a node that trusts a key no snapshot its peers serve is certified under waits at most `SYNC_PEER_WAIT_MS` for a newer one and then stops.
3. *The genesis slice first.* The slice holding the path of `bnum/` ‖ 0 is fetched before any other; its entries must name there the genesis hash the local `kernel_init` stored, or name none where it stored none, as §7.3 requires. A snapshot of another genesis, which its certificates cannot reveal, stops the sync after one slice instead of after the whole state; the node reports it and does not start.
4. *Slices.* Then every non-empty slice, at most `MAX_ACTIVE` (8) at a time and at most `PER_PEER` (2) from one peer, each from one peer from its first page to its last: the node asks for the slice, then again with `after` the last path it received while `more` is true. As each page arrives it checks that every entry is a committed key (10 §2) whose path begins with the slice's bits and is above the one before, writes the entries to a part file under `<dir>/statesync/` and hashes them with `SortedRoot` (§7.1); when `more` is false the slice's subtree must be its summary: no entry for `Empty`, the one entry `(path, value_hash)` for a `Leaf`, `T(S, depth)` for a `Branch`. A page with no entry and `more` true is bad data too. A slice that passes is renamed into place and kept; one that fails is deleted, its peer is not asked again during the sync, and the slice is fetched again from another peer.
5. *Assembly.* Once every slice is in, the node writes the snapshot file: the header, with the entry count the slices hold, and the part files in slice order, which is path order. It loads that file as §7.3 does, which checks the order, the root and the genesis hash once more, deletes `<dir>/statesync/`, and starts the driver, which syncs blocks from `height + 1` from its peers (08 §7a) as after any import.

`solo dev` runs no transport, so it refuses `--sync-from-peers` and `--serve-snapshots` (and `--peer` and `--listen`) rather than ignore them; `--trust-key` says which snapshot to believe and is refused without `--snapshot` or `--sync-from-peers`.

**Failures.** A request unanswered after `REQUEST_TIMEOUT_MS` (10 000 ms) is abandoned and its work handed to another peer; a peer that lets `MAX_STRIKES` (3) requests in a row time out is not asked again during the sync, and any answer resets its count. A peer that disconnects loses its requests at once, without a strike, and is asked again when it reconnects. An answer that does not decode, that is of another kind than the request, or that is bad data as above, bans the peer for the rest of the sync; `Unavailable` only removes the epoch from the peer's offers. When no peer that is not banned offers the target any more, discovery chooses again. The verified slices on disk survive a restart: a node started again with `--sync-from-peers` over the same directory reads the manifest it accepted from `<dir>/statesync/`, verifies it again under its trust, and, when its peers still offer that epoch, fetches only the slices it lacks. Its memory is bounded by the manifest (at most `2^16` summaries), one page per slice in flight and the `SortedRoot` stack of each, whatever the size of the state; its disk holds the slices and, during assembly, the file, twice the state for a moment.

## 8. Bounds and telemetry

The window of spec 20 §5.1 bounds the store: after each seal the host prunes the versions below the oldest the window keeps, deleting their history rows and giving their roots back (§3.2), so the file holds the current state, the nodes the kept roots reach and the history of the window; with `--archive` nothing is pruned. The file does not shrink when rows are deleted: the engine reuses freed pages, and when a file opens with more freed bytes than live ones plus 8 MiB the host compacts it, giving the space back. The engine's page cache is bounded at `CACHE_BYTES` (64 MiB) per store: the engine caches the pages a commit writes as well as those it reads, and at its own default of 1 GiB a node's memory grows with every block it writes until it holds a gigabyte, most of it pages written once and never read again.

### 8.1 Retention of the driver's tables

The driver's tables (08 §7) grow by a proposal, its certificates and a view's votes with every block. A node whose chain state is on disk prunes them, since a restart over its stores executes nothing again and needs none of them (§5): every `PRUNE_EVERY` = 64 finalized heights `f`, it deletes what lies below the *cutoff* `c = min(f − DRIVER_RETENTION, s)`, with `DRIVER_RETENTION` = 1 024 and `s` the height of the latest snapshot record (§6), and nothing while `c` is 0:

- the finalized hash, vote certificate and threshold certificate of every height below `c` (`final/`, `cert/`, `bcert/`), and every proposal (`prop/`) of a height below `c`, finalized or not;
- the block votes, finalize votes, threshold partials and notarized hash of every view below the view of the proposal finalized at `c`, and the first hash each validator signed in those views (`votes/`, `fin/`, `part/`, `notar/`, `sig/`).

The driver's state, the entry and tip certificates, equivocation evidence and the DKG pool stay. What is kept is what consensus can still need: the last 1 024 heights for a peer that fell behind by up to that much and syncs (08 §7a) from this node, and everything from the latest snapshot record's height up, so that the latest snapshot exports (§7.1: its head, its links and `P` all lie above that height) and a node that joins from it syncs from this one. A peer further behind joins from a snapshot. An archive node (`--archive`) prunes nothing, nor does a node whose chain state is in memory, whose restart replays its finalized blocks from these tables (08 §7). The driver store's journal (codex ADR 0036) records writes only: the pruned entries leave the file at its next compaction, and a restart before it reads them back, for the next pass to prune again.

### 8.2 Telemetry

Telemetry (11 §4) reports `solo_store_size_bytes`, the file's size; `solo_store_write_bytes_total`, the bytes of keys, values and nodes written since the node opened, whose increase per block is the store's write amplification; `solo_store_versions`, the versions kept; `solo_store_nodes`, the trie nodes held; and `solo_node_open_seconds`, the time from opening the store to the node being ready. Measured on 2026-10-22 on the reference host (release build, one validator, one transfer per block; `crates/solo-node/tests/store.rs` prints the open time, codex ADR 0037 has the method): a block writes about 8.8 KB to the store over a small state, of which some 64 trie nodes of 101 bytes (the paths of the keys the block and its bookkeeping changed, in the header's trie and in the current one) and the rest keys, values, history and version rows, beside the transaction's own 99 bytes; 11.4 KB per block over the 500 blocks of an archive node, and 15.3 KB over a state of 20 000 accounts, where the paths are deeper. A node reopens in 15 to 18 ms at height 51 or 501, with 52 or 502 versions kept, over one account or 20 000.

## 9. Not in version 0

A snapshot of an epoch whose last block a kernel switch followed (§7.1); a bound on the links, which number the heights between the head and the lowest proposal certified under the trust the latest one's needs, so that a key set handed off long after the epoch's end makes them long; a snapshot of the state behind a block's header root (a snapshot is the sealed state, so proofs at its own height are not served); the vote certificate of the head block verified against the set in the snapshot's own state; eviction of loaded trie nodes from memory; peer discovery beyond the configured peers, and a state sync that fetches a slice's pages from more than one peer.
