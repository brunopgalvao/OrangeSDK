# 09 — Peer-to-peer transport (version 0)

## 1. Overview

Nodes talk over TCP. Each connection carries a sequence of *frames* in both directions; the host maps frames to driver inputs (06 §4.1) and driver effects to frames (06 §4.2). Version 0 is deliberately plain: no encryption, no multiplexing beyond frame tags. Peers are configured by address, or learned from other peers through signed address records (§5a). Authentication of consensus traffic does not depend on the transport, because every consensus message is signed (08 §4).

## 2. Framing

A frame on the wire is a `u32` little-endian byte length followed by a `Frame` in the canonical encoding (06 §2). A frame longer than 16 MiB, or one that does not decode, closes the connection.

```
enum Frame {
  0 Hello    { id: [32], chain_id: u64 }
  1 Message  { topic: u16, payload: bytes }
  2 Tx       { raw: bytes }
  3 Request  { request_id: u64, payload: bytes }
  4 Response { request_id: u64, payload: bytes }
  5 SyncRequest  { request_id: u64, payload: bytes }
  6 SyncResponse { request_id: u64, payload: bytes }
  7 GetPeers     {}
  8 Peers        { records: vec<PeerRecord> }
}
struct PeerRecord { id: [32], addr: bytes, seq: u64, signature: [65] }
```

## 3. Handshake

Both ends send `Hello` first. `id` is the node's validator id (08 §2), or any 32 bytes for a node without a consensus key. A connection whose first received frame is not `Hello`, whose `Hello` names another chain id, or that sends a second `Hello`, is closed. Nothing else is accepted before the handshake.

## 4. Mapping

| Received frame | Driver input / host action |
|---|---|
| `Message { topic, payload }` | `NetworkMessage { peer: id, topic, payload }` |
| `Tx { raw }` | mempool admission as for a locally submitted transaction; rejection is silent |
| `Request { request_id, payload }` | `Request { peer: id, request_id: local, payload }` with a fresh local id the host maps back to `(peer, request_id)` |
| `Response { request_id, payload }` | to the host's catch-up (§6a) when `request_id` is one of its own; `Response { request_id, payload }` otherwise |
| `SyncRequest { request_id, payload }` | answered by the host from the snapshots it serves (22 §7.4), never seen by the driver: a `SyncResponse` with the same `request_id` |
| `SyncResponse { request_id, payload }` | handed to the host's state sync (22 §7.4), if one is running; dropped otherwise |
| `GetPeers`, `Peers { records }` | the host's peer exchange (§5a), never seen by the driver |

| Effect | Frame |
|---|---|
| `Broadcast { topic, payload }` | `Message` to every handshaken peer |
| `Send { peer, topic, payload }` | `Message` to that peer, dropped if not connected |
| `Request { peer, request_id, payload }` | through the host's catch-up (§6a) when the payload is a `SyncRequest` (08 §7a): a `Request` under an id of the host's, or none; otherwise `Request` to that peer |
| `Respond { request_id, payload }` | `Response` with the peer's original id, to the peer that asked |
| `Disseminate`, `PeerScore` | not transported in version 0 |

Every transaction that becomes pending in the mempool (14 §6), local or from a peer, on admission or when a block or a later transaction fills the gap before it, is sent as `Tx` to every peer. Queued transactions stay local. A transaction already sent is not re-sent, and one the pool already holds is not admitted again, which ends gossip loops.

## 5. Connections

A node listens on one address and keeps an outbound connection to each configured peer address, redialling at most every 500 ms. Two nodes that both configure each other hold two connections; consensus is unaffected because votes are deduplicated per validator (08 §5). A node that runs peer exchange (§5a) also dials the peers it learns, up to a target, and limits the connections it accepts.

## 5a. Peer exchange

A node that runs peer exchange starts from its configured peers and its *bootstrap* addresses and learns the rest of the network from them. Codex ADR 0049 records the decisions.

1. *Records.* A node advertises where it listens with a `PeerRecord`: `id` is its node id (its validator id of 08 §2, `keccak256` of its uncompressed secp256k1 public key), `addr` the address peers dial (`ip:port` in ASCII, at most 64 bytes), `seq` its clock in milliseconds when it signed, and `signature` a recoverable secp256k1 signature (`r ‖ s ‖ recovery id`) with the node's key over `keccak256("SOLO-PEER" ‖ chain_id ‖ seq ‖ addr)`, integers little-endian. A record *verifies* when the signature recovers to the public key whose hash is `id` and `addr` parses as a dialable address (not unspecified, not multicast, port not 0). Nobody but the key's holder can make a record for its id, so a peer cannot steer others to its own address under a validator's id. A node without a key, or whose listen address is unspecified and that is given no address to advertise, advertises nothing; it still learns and dials.
2. *Exchange.* Once a connection's handshake completes, each side that runs peer exchange sends `GetPeers`, and repeats it every `EXCHANGE_MS` (10 000 ms). It answers `GetPeers` with a `Peers` frame of at most `MAX_RECORDS` (32) records it holds, its own first, then the current validators', then by score, leaving out the asker's own and every record with a negative score. A connection's `GetPeers` and `Peers` frames are each handled at most once per `PEER_GAP_MS` (1 000 ms); more are dropped. A `Peers` frame with more than `MAX_RECORDS` records, or with a record that does not verify, closes the connection: an honest node forwards only records it verified.
3. *The table.* Learned records go into a *peer table* of at most `TABLE_CAP` (256) entries, one per id, keyed by id. A record for an id the table holds replaces the entry's record only when its `seq` is higher (a moved node re-signs); a node's own id is never entered. An entry is *verified* once this node has dialled its address and the peer's `Hello` named its id. A new entry is refused when its source (the peer that sent it) already accounts for `PER_SOURCE` (16) unverified entries, or when `PER_PREFIX` (8) unverified entries already share its address's prefix (the first 24 bits of an IPv4 address, the first 48 of an IPv6 one; loopback addresses have no prefix limit). When the table is full, a new entry takes the place of the unprotected entry with the lowest score, if that score is negative, and is refused otherwise. Entries of the current validator set and entries this node is connected to are *protected*.
4. *Scores.* An entry starts at 0. A dial that completes a handshake with the expected id adds 10 (at most 100); a dial that fails subtracts 5 (at least −100); a handshake that names another id subtracts 50 and closes the connection. An entry that has failed `MAX_FAILURES` (8) times running and is not of the current validator set is forgotten. A flood of new records therefore never displaces an entry that has answered: new entries start at 0 and replace only entries whose dials failed.
5. *Dialling.* A node keeps up to `outbound` connections it dialled itself (its configured peers included; default 8), and at most `max_peers` connections in all (default 32), configured peers aside. Whenever it has fewer outbound connections than the target, it dials the entries it is not connected to (under any connection) whose next dial is due, current validators first, then by score, then by fewest failures, then by id, at most 8 dials in flight. A dialled connection whose `Hello` has not arrived `HANDSHAKE_MS` (5 000 ms) after it opened is closed and counts as a failed dial; a bootstrap address that answers with the node's own id is not dialled again. A failed dial or a lost connection makes the next one due after `500 ms × 2^(f − 1)`, at most 60 000 ms, where `f` is the number of failures running (one for a lost connection). Bootstrap addresses are dialled the same way, with no id expected until their `Hello` names one, until the node holds its target. It accepts a connection only while it holds fewer than `max_peers` and fewer than `PER_PREFIX` from the connecting address's prefix (loopback aside); others are closed at once. The current validator set is the node's chain state's, read again every 10 000 ms.
6. *What benefits.* Catch-up (§6a) and state sync (§6) ask the handshaken peers; with peer exchange those are every peer the node found, not only those configured. A node syncing its state (§6) exchanges peers as a running one does.

`solo node` runs peer exchange unless `--no-discovery` is given: `--bootstrap <addr>` (repeatable) names bootstrap addresses, `--max-peers <n>` and `--outbound-peers <n>` the limits, and `--advertise <addr>` the address it advertises (default: the listen address, when that is not unspecified). `solo devnet` gives each node every other node as a bootstrap address.

## 6. State sync

A node that joins from its peers' snapshots (22 §7.4) runs its transport before its driver starts: it handshakes as in §3, sends `SyncRequest` frames and takes `SyncResponse` frames, and drops every other frame, since it has no chain state to check messages, transactions or driver requests against; a `SyncRequest` it receives is answered as by a node that serves no snapshot. Once the snapshot is loaded and the driver started, the same connections carry everything else. A serving node answers `SyncRequest` frames whether or not its driver runs; the answers do not depend on its consensus state.

The joining node judges peers itself (22 §7.4): one that answers with data that does not verify, or answers nothing three times running, is not asked again during the sync. The connection stays open, and the peer's consensus traffic is judged as anyone's once the node runs.

## 6a. Block catch-up

The driver asks one peer at a time for finalized blocks (08 §7a) and abandons its request when it enters a view (08 §3). A node that follows a chain whose views last a slot, and whose answers take longer than a slot (a loaded peer, a slow link, a large batch), would drop every answer, ask again, and never catch up. The host therefore keeps the driver's sync requests on the wire across views and serves the driver from the answers it collects. Codex ADR 0046 records the decisions.

1. *Requests.* A `Request` effect whose payload decodes as a `SyncRequest` is not sent as it is. The host notes it as the driver's outstanding request (its id and `from_height`). If an answer it holds *covers* `from_height` (holds the proposal at that height), it steps the driver at once with `Response` under the driver's id, carrying that answer without its proposals below `from_height`. Otherwise, unless a request of its own for the same `from_height` is on the wire, it sends the peer the driver named a `Request` frame with the same payload under an id of its own, at or above `2^63`, which the driver's ids never reach.
2. *Answers.* A `Response` frame to one of the host's ids is the host's. An answer with a certificate and at least one proposal is kept, by the height of its first proposal, and handed to the driver's outstanding request, trimmed as above, when it covers that request's `from_height`; anything else is dropped, and the driver's request is asked again of another peer at the next poll. An answer to an id no longer on the wire is dropped. The driver verifies everything it is handed (08 §7a); the host reads only heights.
3. *Asking ahead.* After keeping an answer whose peer reports a finalized height above it, the host asks the same peer for the batches after it, each starting one past the highest kept answer or, past a request still on the wire, one *stride* (the length of the last answer) past that request's start, with at most *depth* requests on the wire. The depth starts at 1 and grows by one, up to `MAX_DEPTH` (8), for each answer that arrives within a quarter of its wait, halves for a slower one, and falls to 1 when a request times out or the driver refuses an answer. A guessed start that overlaps an earlier answer is trimmed when handed over; one that leaves a gap is filled by the driver's own request.
4. *Retries.* A request unanswered after its wait, `FIRST_WAIT_MS` (1 000 ms) for a first try, is asked again of the next peer in id order that the node heard from within `PEER_TTL_MS` (30 000 ms), the same one when it is the only one, waiting twice as long each time up to `MAX_WAIT_MS` (16 000 ms). Requests and kept answers that hold nothing above the node's finalized height are forgotten, and so is the driver's outstanding request once its `from_height` is finalized.
5. *Refusals.* A kept answer handed to the driver at its request, after whose step the driver's finalized height is still below the answer's first height, was refused: it is dropped, so that it is not handed again, and the next request goes to the wire.

The driver is unchanged: what it receives is always an answer to its outstanding request, and an answer it would have dropped for arriving after it entered another view reaches the request it makes next. Measured in the simulator (`crates/solo-node/tests/catchup.rs`): an observer 120 blocks behind one validator at 60 ms slots, with every answer taking 210 ms, never finalizes a block without this (each answer arrives after its request was abandoned) and catches up in about 0.9 s with it, its depth grown to 8. A node does this by default; turned off (`Node::set_catch_up(false)`, for tests), requests and answers pass through untouched.

## 7. Not in version 0

Encryption and peer authentication (a `Hello` id is self-declared: a record proves which address an id's holder advertised, not that whoever answers there holds the key), a peer table that outlives a restart, rate limits and peer scoring beyond peer exchange's and the state sync's own (§5a, §6), erasure-coded dissemination, and message size limits per topic.
