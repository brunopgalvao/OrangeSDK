# 09 — Peer-to-peer transport (version 0)

## 1. Overview

Nodes talk over TCP. Each connection carries a sequence of *frames* in both directions; the host maps frames to driver inputs (06 §4.1) and driver effects to frames (06 §4.2). There is no multiplexing beyond frame tags. Each end of a connection proves in the handshake that it holds the key behind the id it names (§3), and every frame after the opening `Hello`s is encrypted and authenticated under keys the two ends agree for that connection alone (§3a). Peers are configured by address, or learned from other peers through signed address records (§5a), which a node keeps across restarts (§5a.7). Authentication of consensus traffic does not depend on the transport, because every consensus message is signed (08 §4).

## 2. Framing

A frame in the clear is a `u32` little-endian byte length followed by a `Frame` in the canonical encoding (06 §2). Only each end's first frame, its `Hello`, goes in the clear; every frame after it is *sealed* (§3a). A frame in the clear longer than a `Hello` (`HELLO_LEN`, 140 bytes), a frame longer than `MAX_FRAME` (16 MiB) before it is sealed, or one that does not decode, closes the connection. Until the handshake completes (§3) the only sealed frame accepted is `Auth`, so a sealed frame that would carry more than an `Auth` (`AUTH_LEN`, 66 bytes) closes the connection as soon as its length is read, before the rest of it arrives.

```
enum Frame {
  0 Hello    { version: u16, id: [32], chain_id: u64, genesis: [32], nonce: [32], ephemeral: [33] }
  1 Message  { topic: u16, payload: bytes }
  2 Tx       { raw: bytes }
  3 Request  { request_id: u64, payload: bytes }
  4 Response { request_id: u64, payload: bytes }
  5 SyncRequest  { request_id: u64, payload: bytes }
  6 SyncResponse { request_id: u64, payload: bytes }
  7 GetPeers     {}
  8 Peers        { records: vec<PeerRecord> }
  9 Auth         { signature: [65] }
}
struct PeerRecord { id: [32], addr: bytes, seq: u64, signature: [65] }
```

## 3. Handshake

Every node has a *node key*, a secp256k1 key, and its *node id* is `keccak256` of the key's uncompressed public key (without its `0x04` prefix). A validator's node key is its consensus key, so its node id is its validator id (08 §2); a node without a consensus key uses a key of its own, which may be fresh at every start.

1. *Hello.* Both ends send `Hello` first, in the clear: `version` is the protocol version, `VERSION` (1); `id` is the sender's node id, `chain_id` its chain id, `genesis` its genesis hash (the hash its chain state holds at `bnum/` ‖ 0, 22 §7.3; 32 zero bytes when it holds none), `nonce` 32 bytes it chose for this connection alone, which nobody can predict, and `ephemeral` the SEC1-compressed public key of a secp256k1 key pair it made for this connection alone (§3a). The reference host draws both from a secret taken from the operating system's randomness at start, which it replaces by its hash before every draw (`seed ← keccak256("ORANGE-SEED" ‖ seed)`, then `nonce = keccak256("ORANGE-NONCE" ‖ seed)` and the ephemeral secret `keccak256("ORANGE-EPHEMERAL" ‖ seed)`), so that what it holds at any time tells nothing of the keys of the connections it opened before.
2. *Auth.* On receiving the peer's `Hello`, each end agrees the connection's session (§3a) and sends, sealed, `Auth { signature }`, a recoverable secp256k1 signature (`r ‖ s ‖ recovery id`, as a peer record's, §5a.1) with its node key over

   ```
   keccak256("ORANGE-HELLO" ‖ version ‖ chain_id ‖ genesis ‖ signer_nonce ‖ verifier_nonce ‖ signer_ephemeral ‖ verifier_ephemeral)
   ```

   where `version` (`u16`) and `chain_id` are little-endian, `signer_nonce` and `signer_ephemeral` are the nonce and ephemeral key of the signer's own `Hello`, and `verifier_nonce` and `verifier_ephemeral` those of the `Hello` it received. The signature binds both fresh nonces and both ephemeral keys, in an order that tells the two ends apart, so it answers this connection's challenge alone: it cannot be replayed on another connection, sent back to its signer, or carried to another chain, another genesis or another protocol version; and since it covers the keys the session is agreed over, a party in the middle that put keys of its own in the `Hello`s it relays cannot produce either end's `Auth`.
3. *Completion.* The handshake completes, and the connection's peer is that `id`, when the peer's `Auth` signature recovers to a public key whose hash is the `id` of its `Hello`, checked with the peer's nonce and ephemeral key as the signer's and this node's as the verifier's. Only then is the peer *handshaken*: it counts as connected, receives broadcasts and sends, and has its frames mapped as §4 says; peer exchange's scores (§5a.4) and the catch-up's and state sync's peers (§6, §6a) see only handshaken peers.
4. *Failures.* The connection is closed, and its peer never becomes handshaken, when: the first frame received is not `Hello`, or is longer than one; the `Hello` names another protocol version, another chain id or another genesis hash; its `ephemeral` is not a point of the curve; its `nonce` or its `ephemeral` is this end's own (a connection looped back on itself); the frame after it is longer than an `Auth` (§2), does not open (§3a) or is not `Auth`; the `Auth` signature does not recover, or recovers to a key whose hash is not the `Hello`'s `id`; a `Hello` or an `Auth` arrives after the handshake completed; or the handshake has not completed `HANDSHAKE_MS` (5 000 ms) after the connection opened. Nothing else is accepted before the handshake completes. A connection peer exchange dialled that closes this way counts as a failed dial (§5a.5).

The handshake proves that the key's holder answered this connection's challenge, and the session of §3a carries that proof to every frame after it.

A node of protocol version 0 (whose `Hello` has no `version` and no `ephemeral`) and a node of version 1 refuse each other at the first frame: each end's `Hello` does not decode as the other's, and the connection closes before anything else is read. A later version keeps `version` as the `Hello`'s first field, so that a `Hello` of another version is refused by its number.

## 3a. Sealed frames

Every frame after the `Hello`s, `Auth` included, is sealed under a *session* the two ends agree from their `Hello`s.

1. *Agreement.* Each end computes the ECDH shared secret of its ephemeral secret and the peer's `ephemeral`: the 32-byte x-coordinate of their product on secp256k1. It then forgets its ephemeral secret.
2. *Keys.* HKDF-SHA256 (RFC 5869) extracts a key from the shared secret with the salt `"ORANGE-P2P" ‖ version ‖ chain_id ‖ genesis` (integers little-endian), and expands one 32-byte key per direction: the key of the frames an end *A* sends to an end *B* is the expansion with the info `A_ephemeral ‖ B_ephemeral ‖ A_nonce ‖ B_nonce`. The two directions have different keys, so a frame sent back to its sender does not open.
3. *Sealing.* A sealed frame on the wire is a `u32` little-endian length `L`, then the `Frame`'s canonical encoding encrypted with ChaCha20-Poly1305 (RFC 8439) under the direction's key, then the 16-byte tag; `L` counts the ciphertext and the tag, and is the associated data. The AEAD nonce of the `n`-th frame sent in a direction, counting from 0, is `n` as a `u64` little-endian followed by four zero bytes. Neither end sends the counter: each counts the frames it has sealed and opened.
4. *Opening.* A sealed frame closes the connection when `L` is below 16 or above `MAX_FRAME + 16` (`AUTH_LEN + 16` before the handshake completes, §2), when it does not open under the receiving direction's key and the next counter, or when what it opens to does not decode. A frame altered on the way, replayed, reordered, dropped from between two others, injected, or sent in the clear therefore closes the connection, since its tag fails under the nonce the receiver expects. A direction that would seal or open its `2^64 − 1`-th frame closes the connection instead.
5. *What it gives.* A passive observer of a connection sees the two `Hello`s (ids, chain, genesis, nonces and ephemeral keys) and the length of every frame; nothing of what the frames carry. An active one cannot alter, replay, reorder, drop from the middle or inject frames without closing the connection, and cannot read or write frames under either end's id without that end's node key, because the `Auth` each end sends is sealed under the session and signs the ephemeral keys it is agreed over (§3). Since the ephemeral secrets are forgotten once the keys are derived, the node key of either end, taken later, opens no recorded session (forward secrecy). Truncation is not hidden: an observer, or a party that closes the connection, can end a connection at any frame boundary, as it always could.
6. *Cost.* A sealed frame is 16 bytes longer than the frame it carries. Measured with the reference host's code on one core of an Apple M4 Pro (release build, 2026-11-02), agreeing a session takes about 40 µs per end; sealing and opening together take about 1.1 µs for a 200-byte frame (a vote) and about 3.2 ms for a 1 MiB frame (about 330 MB/s for both ends' work on one core), against 0.06 µs and 29 µs to encode the same frames.

## 4. Mapping

| Received frame | Driver input / host action |
|---|---|
| `Message { topic, payload }` | `NetworkMessage { peer: id, topic, payload }` |
| `Tx { raw }` | mempool admission as for a locally submitted transaction; rejection is silent |
| `Request { request_id, payload }` | `Request { peer: id, request_id: local, payload }` with a fresh local id the host maps back to `(peer, request_id)`. The host holds at most `MAX_SERVING` (8) of one peer's requests waiting for the driver's answer: one past them is answered at once with a `Response` of an empty payload, without a driver step; one the driver has not answered within `SERVE_MS` (10 000 ms) is answered the same way and forgotten, and the requests of a peer no longer connected are forgotten. An empty answer is no answer to the asker (§6a, step 2) |
| `Response { request_id, payload }` | to the host's catch-up (§6a) when `request_id` is one of its own; `Response { request_id, payload }` otherwise. Either only from the peer the request went to: a `Response` from any other peer, or to an id no request is waiting on, is dropped (§6a, step 2) |
| `SyncRequest { request_id, payload }` | answered by the host from the snapshots it serves and, for handoffs, from its chain state (22 §7.4), never seen by the driver: a `SyncResponse` with the same `request_id` |
| `SyncResponse { request_id, payload }` | handed to the host's state sync (22 §7.4), if one is running; dropped otherwise |
| `GetPeers`, `Peers { records }` | the host's peer exchange (§5a), never seen by the driver |

| Effect | Frame |
|---|---|
| `Broadcast { topic, payload }` | `Message` to every handshaken peer |
| `Send { peer, topic, payload }` | `Message` to that peer, dropped if not connected |
| `Request { peer, request_id, payload }` | through the host's catch-up (§6a) when the payload is a `SyncRequest` (08 §7a): a `Request` under an id of the host's, or none; otherwise `Request` to that peer |
| `Respond { request_id, payload }` | `Response` with the peer's original id, to the peer that asked |
| `Disseminate`, `PeerScore` | not transported in version 0 |

Every transaction that becomes pending in the mempool (14 §6), local or from a peer, on admission or when a block or a later transaction fills the gap before it, is sent as `Tx` to every peer. Queued transactions stay local. A transaction already sent is not re-sent to the peers it went to, and one the pool already holds is not admitted again, which ends gossip loops. A peer that was not connected when a transaction was sent would never hear of it, and a transaction a node accepted while it had no peer would reach nobody: an observer, which never proposes, would hold it for ever. So once a connection's handshake completes (§3), the node sends that peer, as `Tx` frames, every pending transaction its pool holds, by sender and then nonce, as long as their raw bytes total at most `POOL_SYNC_BYTES` (4 MiB); the peer admits those it lacks, and the ones it holds end there.

## 5. Connections

A node listens on one address and keeps an outbound connection to each configured peer address, redialling at most every 500 ms. Two nodes that both configure each other hold two connections; consensus is unaffected because votes are deduplicated per validator (08 §5). Whether or not it runs peer exchange, a node accepts a connection only while it holds fewer than `max_peers` (default 32) connections besides those to its configured peers, and closes others at once. A node that runs peer exchange (§5a) also dials the peers it learns, up to a target, and limits the connections it accepts from one prefix.

## 5a. Peer exchange

A node that runs peer exchange starts from its configured peers and its *bootstrap* addresses and learns the rest of the network from them. Codex ADR 0049 records the decisions.

1. *Records.* A node advertises where it listens with a `PeerRecord`: `id` is its node id (its validator id of 08 §2, `keccak256` of its uncompressed secp256k1 public key), `addr` the address peers dial (`ip:port` in ASCII, at most 64 bytes), `seq` its clock in milliseconds when it signed, and `signature` a recoverable secp256k1 signature (`r ‖ s ‖ recovery id`) with the node's key over `keccak256("ORANGE-PEER" ‖ chain_id ‖ seq ‖ addr)`, integers little-endian. A record *verifies* when the signature recovers to the public key whose hash is `id` and `addr` parses as a dialable address (not unspecified, not multicast, port not 0). Nobody but the key's holder can make a record for its id, so a peer cannot steer others to its own address under a validator's id. A node without a consensus key (whose node key may change at every start, §3), or whose listen address is unspecified and that is given no address to advertise, advertises nothing; it still learns and dials.
2. *Exchange.* Once a connection's handshake completes, each side sends `GetPeers`, and repeats it every `EXCHANGE_MS` (10 000 ms); a node that does not run peer exchange sends it too, which keeps the connection from going idle at the other end (§5b.3), and ignores both the question and the answer. A node that runs it answers `GetPeers` with a `Peers` frame of at most `MAX_RECORDS` (32) records it holds, its own first, then the current validators', then by score, leaving out the asker's own and every record with a negative score. A connection's `GetPeers` and `Peers` frames are each handled at most once per `PEER_GAP_MS` (1 000 ms); more are dropped. A `Peers` frame with more than `MAX_RECORDS` records, or with a record that does not verify, closes the connection: an honest node forwards only records it verified.
3. *The table.* Learned records go into a *peer table* of at most `TABLE_CAP` (256) entries, one per id, keyed by id. A record for an id the table holds replaces the entry's record only when its `seq` is higher (a moved node re-signs); a node's own id is never entered. An entry is *verified* once this node has dialled its address and the handshake there completed (§3) under its id. A new entry is refused when its source (the peer that sent it) already accounts for `PER_SOURCE` (16) unverified entries, or when `PER_PREFIX` (8) unverified entries already share its address's prefix (the first 24 bits of an IPv4 address, the first 48 of an IPv6 one; loopback addresses have no prefix limit). When the table is full, a new entry takes the place of the unprotected entry with the lowest score, if that score is negative, and is refused otherwise. Entries of the current validator set and entries this node is connected to are *protected*.
4. *Scores.* An entry starts at 0. A dial that completes a handshake with the expected id adds 10 (at most 100); a dial that fails, a handshake that fails (§3) included, subtracts 5 (at least −100); a handshake that completes under another id subtracts 50 and closes the connection. An entry that has failed `MAX_FAILURES` (8) times running and is not of the current validator set is forgotten. A flood of new records therefore never displaces an entry that has answered: new entries start at 0 and replace only entries whose dials failed.
5. *Dialling.* A node keeps up to `outbound` connections it dialled itself (its configured peers included; default 8), and at most `max_peers` connections in all (default 32), configured peers aside. Whenever it has fewer outbound connections than the target, it dials the entries it is not connected to (under any connection) whose next dial is due, current validators first, then by score, then by fewest failures, then by id, at most 8 dials in flight. A dialled connection whose handshake has not completed `HANDSHAKE_MS` (5 000 ms) after it opened is closed (§3) and counts as a failed dial; a bootstrap address that answers with the node's own id is not dialled again. A failed dial or a lost connection makes the next one due after `500 ms × 2^(f − 1)`, at most 60 000 ms, where `f` is the number of failures running (one for a lost connection). Bootstrap addresses are dialled the same way, with no id expected until their `Hello` names one, until the node holds its target. It accepts a connection only while it holds fewer than `max_peers` and fewer than `PER_PREFIX` from the connecting address's prefix (loopback aside); others are closed at once. The current validator set is the node's chain state's, read again every 10 000 ms.
6. *What benefits.* Catch-up (§6a) and state sync (§6) ask the handshaken peers; with peer exchange those are every peer the node found, not only those configured. A node syncing its state (§6) exchanges peers as a running one does.
7. *Persistence.* A node with a data directory keeps its table across restarts in the file `peers.records` there. An entry is *seen* once a dial of it has completed a handshake (§3), and keeps the time of the last such handshake, `seen_ms`, in this node's clock. The file is the canonical encoding (06 §2) of `vec<SavedPeer>`, `struct SavedPeer { record: PeerRecord, seen_ms: u64 }`: the seen entries, at most `max_peers` of them, current validators first, then by score, then by id. It is written at most every `SAVE_MS` (10 000 ms) when it would change, and when the transport stops, to a temporary file renamed into place, so a crash leaves the old file or the new one; a write that fails is retried at the next turn and stops nothing. At start, before its first dial, the node reads the file and enters each saved record as its holder's own (no source, §5a.3, so the per-source limit does not apply and the per-prefix and capacity limits do), with its score at 0, its failures at 0, unverified, and its `seen_ms` kept. It skips, without failing, every saved record that does not verify (§5a.1, against its own chain id), whose id is its own, whose `seen_ms` is more than `SAVED_TTL_MS` (7 days, 604 800 000 ms) before its clock, and every one past the first `max_peers`. A file that is missing, cannot be read or does not decode is taken as empty, and is replaced at the next write. A restarted node therefore dials the peers it last had before its bootstrap addresses answer, and each must complete a handshake again to be verified.

`orange node` runs peer exchange unless `--no-discovery` is given: `--bootstrap <addr>` (repeatable) names bootstrap addresses, `--max-peers <n>` (which also applies with `--no-discovery`, §5) and `--outbound-peers <n>` the limits, and `--advertise <addr>` the address it advertises (default: the listen address, when that is not unspecified). `orange devnet` gives each node every other node as a bootstrap address.

## 5b. What a connection may cost

One thread runs a node's transport and its driver, and so its consensus, so the transport bounds what any one connection can make it do, handshaken or not.

1. *Reading.* In one poll a node reads at most `READ_BYTES` (1 MiB) from a connection, and nothing while a whole sealed frame of the longest kind (`4 + MAX_FRAME + 16` bytes) could be waiting unhandled, and handles at most `READ_FRAMES` (256) of its frames; the rest wait for the next poll. Bytes handled are dropped from the front of the connection's buffer only once they are at least as many as the bytes that remain, so every byte is moved a bounded number of times however short its frames: removing each frame from the front as it is handled moves the rest of the buffer every time, and a peer streaming 21-byte frames made that cost about 0.4 s per buffered MiB.
2. *Writing.* At most `MAX_OUTPUT` (32 MiB) is queued for a connection; a frame that would queue more closes it instead. While `OUTPUT_HIGH` (8 MiB) or more is queued, the connection is not read and none of its frames are handled, so a peer that asks and never reads the answers is not served more: a `SyncRequest` of about 50 bytes buys a snapshot page of up to 1 MiB (22 §7.4), a catch-up `Request` of about 30 bytes up to 16 blocks (08 §7a). The cap holds the mark, an answer of up to `MAX_FRAME` to the last frame handled below it, and broadcasts. A connection with output queued that takes none of it for `WRITE_STALL_MS` (30 000 ms) is closed.
3. *Idling.* A connection from which nothing is read for `IDLE_MS` (60 000 ms) is closed; time it spends unread under 2 does not count. Every handshaken peer is sent `GetPeers` every `EXCHANGE_MS` (§5a.2), so no honest connection idles that long, and a connection still in its handshake closes after `HANDSHAKE_MS` (§3).

## 6. State sync

A node that joins from its peers' snapshots (22 §7.4) runs its transport before its driver starts: it handshakes as in §3, sends `SyncRequest` frames and takes `SyncResponse` frames, and drops every other frame, since it has no chain state to check messages, transactions or driver requests against; a `SyncRequest` it receives is answered as by a node that serves no snapshot and holds no chain state: no offers, no handoffs. Once the snapshot is loaded and the driver started, the same connections carry everything else. A serving node answers `SyncRequest` frames whether or not its driver runs; the answers do not depend on its consensus state. Every node with chain state answers requests for handoffs (22 §7.4), so that a joining node trusting an older key set can follow the chain's key from it (22 §7.5).

The joining node judges peers itself (22 §7.4): one that answers with data that does not verify, or answers nothing three times running, is not asked again during the sync. The connection stays open, and the peer's consensus traffic is judged as anyone's once the node runs.

A sync never waits for ever for peers. A peer counts while it is handshaken, still asked under the rule above, and offers something other than snapshots the node set aside under its trust (22 §7.4). While no peer counts, the sync fails, and the node stops with the reason, as soon as a peer's `Hello` has named its chain id with another genesis hash (§3; the node was pointed at another chain), and otherwise once no peer has counted for `SYNC_PEER_WAIT_MS` (60 000 ms) running, counted from its first poll or from the moment its last counting peer left or stopped being asked.

## 6a. Block catch-up

The driver asks one peer at a time for finalized blocks (08 §7a) and abandons its request when it enters a view (08 §3). A node that follows a chain whose views last a slot, and whose answers take longer than a slot (a loaded peer, a slow link, a large batch), would drop every answer, ask again, and never catch up. The host therefore keeps the driver's sync requests on the wire across views and serves the driver from the answers it collects. Codex ADR 0046 records the decisions.

1. *Requests.* A `Request` effect whose payload decodes as a `SyncRequest` is not sent as it is. The host notes it as the driver's outstanding request (its id and `from_height`). If an answer it holds *covers* `from_height` (holds the proposal at that height), it steps the driver at once with `Response` under the driver's id, carrying that answer without its proposals below `from_height`. Otherwise, unless a request of its own for the same `from_height` is on the wire, it sends the peer the driver named a `Request` frame with the same payload under an id of its own, at or above `2^63`, which the driver's ids never reach.
2. *Answers.* A `Response` frame to one of the host's ids is the host's, and counts only when it comes from the peer that request went to: ids are sequential, so any peer can guess them, and an answer from another peer is dropped and the request stays on the wire, so that no peer can take an honest peer's answer's place, nor raise the sync alert of step 6 for blocks another peer was asked for. The driver's own requests that go to the wire as they are (one whose payload is not a `SyncRequest`, or any with catch-up off) are bound to their peers the same way: the host remembers the peer of each of the last `MAX_PASSED` (64), and hands the driver one answer to each, from that peer; any other `Response` under an id below `2^63` is dropped. An answer is *consecutive* when its proposals' heights are `from_height`, `from_height + 1`, … in order, with `from_height` the request's; heights are the sender's to choose, so they are checked without arithmetic that could overflow. An answer with a certificate and at least one proposal that is consecutive is kept, by the height of its first proposal, and handed to the driver's outstanding request, trimmed as above, when it covers that request's `from_height`; anything else is dropped, as no answer, and the driver's request is asked again of another peer at the next poll. An answer to an id no longer on the wire is dropped. The driver verifies everything it is handed (08 §7a); the host reads only heights.
3. *Asking ahead.* After keeping an answer whose peer reports a finalized height above it, the host asks the same peer for the batches after it, each starting one past the highest kept answer or, past a request still on the wire, one *stride* (the length of the last answer) past that request's start, and none when that start would pass `2^64 − 1`, with at most *depth* requests on the wire. The depth starts at 1 and grows by one, up to `MAX_DEPTH` (8), for each answer that arrives within a quarter of its wait, halves for a slower one, and falls to 1 when a request times out or the driver refuses an answer. A guessed start that overlaps an earlier answer is trimmed when handed over; one that leaves a gap is filled by the driver's own request.
4. *Retries.* A request unanswered after its wait, `FIRST_WAIT_MS` (1 000 ms) for a first try, is asked again of the next peer in id order that the node heard from within `PEER_TTL_MS` (30 000 ms), the same one when it is the only one, waiting twice as long each time up to `MAX_WAIT_MS` (16 000 ms). Requests and kept answers that hold nothing above the node's finalized height are forgotten, and so is the driver's outstanding request once its `from_height` is finalized: the host then steps the driver with an empty `Response` under that request's id, which the driver drops, so that it is free to ask again. A driver waits for the answer to its outstanding request until it enters another view (08 §7a), and a node whose peers have all moved on to the next epoch may never enter one without the blocks it would ask for.
5. *Refusals.* A kept answer handed to the driver at its request is spent: it is dropped after the step, so that it is not handed again. The driver takes an answer whole or not at all, so what remains of one it took is only the suffix proposals after an epoch's last block (08 §3a), which it never takes. If the driver's finalized height is still below the answer's first height, the answer was refused, and the next request goes to the wire. A driver that asks again for the same blocks within the step it was handed the answer in has refused it too: the answer is dropped then, not at the step's end, and that request goes to the wire, so a driver that asks again at once is never handed the same answer twice in one step.

6. *Out of reach.* An answer with no proposal, from a peer that reports a finalized height at or above the height asked for, says that the peer no longer holds that block: it pruned it (22 §8.1). The host then raises its *sync alert*, `block h is no longer kept by its peers (one has finalized F): this node is further behind than its peers keep blocks; restart it over an empty data directory with --sync-from-peers or --snapshot`, logs it once when it is raised and reports it in `/status` as `syncAlert` (11 §6), which `orange doctor` reports (11 §7). An answer that holds blocks, or the node's finalized height moving past `h − 1`, clears it. The host and the driver go on asking, since an archive peer, or one that joined from an older snapshot, may still serve the block.

The driver is unchanged: what it receives is always an answer to its outstanding request, and an answer it would have dropped for arriving after it entered another view reaches the request it makes next. Measured in the simulator (`crates/orange-node/tests/catchup.rs`): an observer 120 blocks behind one validator at 60 ms slots, with every answer taking 210 ms, never finalizes a block without this (each answer arrives after its request was abandoned) and catches up in about 0.9 s with it, its depth grown to 8. A node does this by default; turned off (`Node::set_catch_up(false)`, for tests), requests and answers pass through untouched.

## 7. Not in version 0

Hiding the ids, chain and frame lengths from a passive observer (the `Hello`s go in the clear, §3a.5), rekeying within a connection (a connection lives no longer than its counters, §3a.4), rate limits beyond the budgets of §5b, peer scoring beyond peer exchange's and the state sync's own (§5a, §6), erasure-coded dissemination, and message size limits per topic.
