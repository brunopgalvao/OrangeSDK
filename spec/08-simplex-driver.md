# 08 — The reference driver: Simplex consensus

## 1. Overview

This document specifies the consensus protocol of the reference kernel's driver (06 §3): a Simplex-family BFT protocol with fused finality. It is the protocol `orange dev` runs with one validator and what multi-validator chains run until governance installs another kernel. It fixes the messages, the voting rules, how nodes that drifted into different views meet again, how the validator set changes between epochs, the certificates carried by `FinalizeBlock`, equivocation evidence, and what the driver persists. Networking, timers and keys are the host's (05 §4.5–4.6); execution is the state-transition group's (06 §5); stake, epochs, slashing and the threshold key are spec 15's.

Tolerance: validators are weighed by stake. A set of votes from distinct validators is a *quorum* when their weights sum to more than two thirds of the total weight of the set: `3 · Σ weight(voters) > 2 · Σ weight(set)`. The protocol is safe and live while the faulty validators hold less than a third of the weight. With equal weights a quorum is `⌊2n/3⌋ + 1` of `n` validators; a set whose total weight is zero has no quorum.

## 2. Validators and identity

`Genesis.validators` is a `ValidatorSet { validators: vec<Validator { id: [32], weight: u64 }> }` in canonical encoding: the set of epoch 0. A validator's `id` is `keccak256` of its uncompressed secp256k1 public key (64 bytes); its `weight` is its stake in gwei (15 §1). Without staking (`epoch_blocks = 0`, 15 §2) it is the only set; with staking, the set of each later epoch is decided in chain state at the end of the epoch before (15 §4). The order of a set is the leader rotation of its epoch's views; the leader of view `v` is `validators[(v − 1) mod n]` of the set of `v`'s epoch (§3a).

A node learns whether it is a validator by signing the identity message (§4) with key role 0 through `sign`, recovering the public key with `secp256k1_recover`, and looking the id up in the set of its current epoch. A node without a key, or with a key outside the set, is an observer: it follows the protocol's messages, executes and finalizes exactly as validators do, and never votes. Every validator index in a message, a certificate or evidence indexes the set of the epoch of the view it names.

## 3. Views and the notarized tip

The driver runs in views `v = 1, 2, …`. Every node keeps a *notarized tip*: the proposal with the highest view that it has seen notarized (§5), initially the empty tip at height 0 with hash zero, whose timestamp is the node's clock when it starts, or the genesis time (20 §3.4) if that is later, so that the first block is proposed one slot after both. A proposal in view `v` extends the proposer's tip: its `parent` is the tip's hash and its `height` is the tip's height plus one. Views only increase; a node may enter a view several above its current one (§5).

Entering view `v`, a node:

1. clears its `voted`, `timed_out` and `proposing` flags;
2. *arms* the view: sets the *timeout timer* of `v` (id `2v`) to `now + T`, where the *view timeout* `T` is `3 × slot_ms × 2^b` and `b` is its backoff (§5a); if it is the leader of `v`, has neither voted nor timed out in `v` and its signing guard does not forbid it (§7b), it proposes at `max(now, tip.timestamp_ms + slot_ms)`: immediately, or when the *proposal timer* of `v` (id `2v + 1`) fires. Arming also abandons an outstanding sync request (§7a) and forgets which peers were answered (§5a).

A node that restarts (`Started`) arms its current view without clearing `voted` or `timed_out`, so it never votes twice in one view and a leader never proposes twice in one view. A node that starts with no state record at all cannot know what it signed, and starts under the signing guard of §7b.

Timers of other views are ignored when they fire. `slot_ms` is `GenesisParams.slot_ms`.

## 3a. Epochs of views

With staking, views belong to epochs: the *epoch of view* `v` is `v >> 32`, and epoch `e`'s views start at `first_view(e) = e · 2^32 + 1`. Without staking every view is in epoch 0. The validator set of a view's epoch proposes, votes and certifies in it; quorums of a view are weighed by that set.

Epoch `e` ends with its last block, the block at height `end(e)` (15 §4). A proposal in a view of epoch `e` whose height is above `end(e)` is a *suffix* proposal: it carries no transactions, no evidence, no DKG envelopes and no anchor, and validators vote for it only if it carries no transactions, evidence or envelopes. A suffix proposal exists only to finalize the last block when that block's own finalize quorum did not form; finalizing one finalizes its ancestors up to `end(e)`, and never the suffix itself, which is not executed, gets no height of its own in chain state and no threshold certificate.

A node enters epoch `e + 1` when it has executed `end(e)`, which is when chain state holds the set of `e + 1`: it enters `first_view(e + 1)` (if not already past it) with `end(e)` as its tip and the finalize certificate of `end(e)` as its tip and entry certificate, looks itself up in the new set, and arms the view. The views of epoch `e` are over for it: proposals and votes of epoch `e` are stale (§5a), and finalize votes, certificates and notarizations of epoch `e` change nothing but evidence (§9). A node that receives a message for a view of an epoch it has not entered cannot know that epoch's set yet, so it checks only that the message's signature (for a `Certificate`, its first vote's) recovers to a validator registered in its chain state that is not jailed (15 §3). Such a *verified* message for the next epoch is kept, at most 64 in all and at most 4 per signer, each with its delivering peer and signer, and taken up again when the node enters that epoch; the node asks the delivering peer of any verified message for finalized blocks (§7a). A message for a later epoch that fails the check is never kept; it may still ask its peer for blocks, as a *weak* request that any verified trigger replaces (§7a), so a node far behind a chain whose set has changed completely can still catch up, and a peer that sends unverifiable messages and never answers cannot hold its catch-up up. A node whose chain state is behind the epoch of its view (it lost its chain state) works in the epoch of the next block it executes, and acts in its view's epoch only once it has caught up.

## 4. Messages

All consensus traffic is on topic 1 with a `ConsensusMessage` payload. `Propose`, `Vote`, `Finalize`, `FinalizeShare` and `Dkg` are `Broadcast`; `Certificate` and `Fetch` are `Send` to one peer (§5a).

```
enum ConsensusMessage {
  0 Propose       { proposal: Proposal, signature: [65] }
  1 Vote          { view: u64, hash: [32], signature: [65] }   // hash zero: timeout vote
  2 Finalize      { view: u64, hash: [32], signature: [65] }
  3 Certificate   { certificate: Certificate, proposal: option<Proposal> }
  4 FinalizeShare { view: u64, hash: [32], signature: [65], partials: vec<PartialShare> }
  5 Dkg           { envelope: bytes }                          // an encoded DkgEnvelope, 15 §6.2
  6 Fetch         { view: u64, signature: [65] }               // asks a leader for its tip, §5a
}
struct Proposal { view: u64, height: u64, parent: [32], timestamp_ms: u64, anchor_height: u64, anchor_root: [32], txs: vec<bytes>, evidence: vec<Evidence>, dkg: vec<bytes> }
struct PartialShare { key_set: u64, index: u32, signature: bytes }
```

The *proposal hash* is `keccak256` of the encoded `Proposal`. The fields before `txs` have fixed sizes, so the *anchor* (`anchor_height`, `anchor_root`) is at bytes 56 to 95 of every encoded proposal, where a contract reads it without decoding the rest (spec 17 §4). An anchor of height 0 with a zero root is *none*. Signatures are recoverable secp256k1 signatures (`r ‖ s ‖ recovery id`) over `keccak256(kind ‖ chain_id ‖ view ‖ hash)` with every integer little-endian and `kind` one byte: 0 for a proposal, 1 for a vote, 2 for a finalize vote, 3 for a DKG envelope (15 §6.2, where `view` is the epoch), 4 for a `Fetch` (signed over its `view` and the zero hash). The identity message of §2 is a vote (`kind` 1) in view 0 on the zero hash. Signing is deterministic (RFC 6979), so a node that signs the same message twice produces the same bytes.

`FinalizeShare` is a finalize vote that also carries the voter's threshold partial signatures, one per share it holds (§6a): its `view`, `hash` and `signature` are exactly a `Finalize`'s, and receivers treat it as one. `Dkg` carries a DKG envelope (15 §6.2): a DKG message, a confirmation, a handoff or threshold evidence for leaders to put in proposals, or a rotation share that nodes only gather (15 §6.6).

A message whose signature does not recover to a validator is dropped. A `Propose` must be signed by the leader of its view; one for view 0 is dropped. `Certificate` and `Fetch` are checked as §5a says.

## 5. Rules

Let `q` be the quorum and `v` the node's current view. A node:

- **Proposes** (leader only) by taking the mempool (`MempoolTake` with `max_bytes` 2^20, `max_gas` the block gas limit, 30 000 000, and `skip` the hashes of the transactions that the ancestors of the tip above the executed height carry, so that a block on an unexecuted parent gets a full budget of new transactions), building `Proposal { view, height: tip.height + 1, parent: tip.hash, timestamp_ms: max(now, tip.timestamp_ms + 1), anchor_height, anchor_root, txs, evidence, dkg }` with at most `max_txs` transactions, the pending evidence of §9 (at most 8 records) and at most 16 DKG envelopes from its pool (15 §6.2), in pool order, leaving out each envelope that would make the encoded proposal longer than `MAX_PROPOSAL_BYTES` (below), or with all three empty and no anchor for a suffix proposal (§3a), the anchor being the height of the last block it executed and that block's `state_root` (none before the first block), broadcasting `Propose`, and then handling its own proposal as below. `txs` are the mempool's in the order the host gave them, leaving out every transaction that an ancestor of the tip above the executed height carries, and every transaction that has run (its receipt records gas used). A leader extends its tip before executing it, since blocks execute on finalization, and until then its mempool still holds the tip's transactions.
- **Votes** for the first valid proposal it sees in view `v` that extends its tip, is *timely*, carries at most `max_txs` transactions (`GenesisParams.max_txs`), at most 8 evidence records and at most 16 DKG envelopes, is at most `MAX_PROPOSAL_BYTES = 2^21` bytes encoded, and is empty if it is a suffix proposal (§3a), provided it has neither voted nor timed out in `v` and its signing guard does not forbid it (§7b); it sets `voted` and broadcasts `Vote { view, hash }`. Its own vote counts. The vote is due whenever these conditions come to hold, not only when the proposal arrives: a node that holds the leader's proposal for `v` (the first one it saw signed by the leader) votes for it when it enters `v`, if the proposal arrived first, and when a notarization makes the proposal's parent its tip. Otherwise a node one message behind the leader, which a jittery network makes common, never votes in the leader's view, and views whose quorum needs it time out with every validator honest.
  The size bounds keep what one leader can make every node store within what an honest leader makes. An honest proposal carries at most `max_txs` transactions, of at most 2^20 bytes in all (the mempool take above), and its evidence and fixed fields take under 2 KiB, so it is always under the cap, with about a MiB left for envelopes, which the leader fits in; should the host hand it more transactions than it asked for, it leaves out the last ones until the proposal fits. A `Propose` or a `Certificate` carrying a proposal of the cap fits in a frame of 09 §2 (16 MiB) eight times over. Without the bounds a faulty leader could fill each of its turns with a frame's worth of transactions, and every one of them, valid or not, leaves its receipt and its raw bytes in chain state for good.
  A proposal is *timely* when `parent_ms < timestamp_ms ≤ now + MAX_DRIFT_MS`, with `now` the voter's clock when it considers the proposal, `MAX_DRIFT_MS = 1 000` and `parent_ms` the timestamp of the tip it extends: the tip proposal's, or for the first block (a tip at height 0) the genesis block's, the genesis time of 20 §3.4 (0 for a genesis without one), not the node's own initial tip time, which differs from node to node and only paces its first proposal (§3). The rule holds for every proposal, suffix proposals included: a suffix becomes the tip, and its timestamp paces the next leader just as a block's does. So block timestamps rise strictly from the genesis block's (20 §3.4), and no leader can set one far ahead: a leader proposes one slot after its tip's timestamp (§3), so a tip from a faulty leader with a timestamp `10^12` ms ahead would keep every later leader waiting past every view timeout, and the chain would halt. An honest leader's timestamp `max(now, tip.timestamp_ms + 1)` is always above its parent's, and is past a voter's clock only by the difference between the two clocks, less the message delay; `MAX_DRIFT_MS` tolerates that difference up to one second, many times what clock synchronization (NTP) leaves between hosts, and bounds what one faulty leader can do to about one second: its block's time is at most a second ahead, and the next leader waits at most that second plus a slot, at worst one view timeout, which is what a leader that does not propose at all costs. A proposal refused as untimely is not considered again when time passes, except as the vote for a held proposal above is (on entering the view, or when its parent becomes the tip); an untimely proposal is not evidence.
- **Times out** when the timeout timer of `v` fires: it sets `timed_out`, broadcasts `Vote { view: v, hash: zero }` and re-arms the timer to `now + T`. Every later firing in the same view repeats the same timeout vote, which peers may have missed, and forgets which peers were answered (§5a). A node may both vote for a proposal and time out in the same view.
- **Notarizes** a proposal when it holds, for some view `w`, a quorum of votes for `(w, hash)` or a quorum of finalize votes for it (a finalize quorum implies a notarization). If it knows the proposal and `w` is above its tip's view, the proposal becomes its tip. If `w ≥ v`, it enters view `w + 1`; it then broadcasts its finalize vote for `(w, hash)` (its own finalize vote counts) when it knows the proposal, did not time out in `w` and its signing guard does not forbid it (§7b), as a `FinalizeShare` with its partial signatures when it holds shares of the active key set, the proposal is not a suffix and it can vouch for the proposal's anchor (§6a), as a `Finalize` otherwise; and when it lacks the proposal, it sends a sync request (§7a) to the peer that delivered the quorum.
- **Skips** when it holds a quorum of timeout votes for some view `w ≥ v`: it enters `w + 1` with its tip unchanged.
- **Finalizes** the proposal at `(view, hash)` when it holds a quorum of finalize votes for it and knows the proposal and every ancestor down to its finalized height: it emits `ExecuteBlock` for each unexecuted ancestor and the proposal that is not a suffix proposal, lowest height first, stores the finalize certificate for each (and the threshold certificate of §6a, if it combined one), and records the new finalized height. On each `BlockExecuted` it emits `FinalizeBlock { height, certificate }` and a `blocks` metric, then does its DKG duties (15 §6.3) and, after the last block of its epoch, enters the next epoch (§3a).

Votes and proposals for views at or above `v` are kept, whether or not they complete a quorum yet; finalize votes are kept for any view of the current epoch, with the partial signatures they carry (one per key set and share index, and only when the partial's share index names the voter in that key set's shareholders). A vote or proposal for a view below `v` is not counted. It is *stale*: its sender may be stuck in that view, and the node answers it as §5a says. The one exception is a proposal below `v`, in the current epoch, that the node holds a vote or finalize quorum for but lacked: it is kept, may become the tip, and may complete a finalization.

`ExecuteBlock` carries `Block { header, txs, participation }` where `participation` is the encoded `Participation { evidence, dkg }` of the proposal (§9, 15 §6.2).

## 5a. View synchronization

Validators that start at different times, restart, or lose messages drift into different views; a quorum then never forms in any one view unless they meet. The first three rules make them meet; the fourth keeps views notarizing when the network or the nodes are slower than the base timeout; the fifth lets validators vote for a leader whose tip they lack:

1. A quorum for any view at or above the current one moves a node past that view (§5, notarizes and skips).
2. A node stuck in a view repeats its timeout vote every view timeout (§5, times out).
3. **Certificate forwarding.** Every node remembers its *entry certificate*, the quorum that brought it into its current view (timeout votes, block votes, or finalize votes, as `Certificate { kind, view, hash, votes }` with `kind` 1 or 2), and its *tip certificate*, the quorum that made its tip the tip. When a node receives a stale `Propose` or `Vote` from a peer, or a `Propose` for its current view or a later one whose height is at most its tip's height (the leader lacks the node's tip, and, since a notarized tip need not be finalized, catch-up cannot bring it), it sends that peer, point to point, `Certificate { certificate: tip certificate, proposal: tip }` unless the tip certificate is also the entry certificate, then `Certificate { certificate: entry certificate, proposal }` with the proposal the entry certificate names, if it names one the node holds. It answers only when the stale message's signature verifies against the set of its view's epoch and its signer's validator id is the delivering peer's id (the `Hello` id of 09), because any validator's old signed message stays valid forever and proves nothing about whoever replays it. It answers at most once per peer until it enters another view or its timeout fires again, a budget that stale messages, proposals at or below its tip and `Fetch` (rule 5) share. They can therefore draw at most two certificates and one proposal per validator per view and timeout period out of a node; that bounds the amplification but does not remove it, since the answer is far larger than the message that draws it (§8). A stale vote is not answered at all when it is a block vote, in the view just before the current one, for the proposal the node notarized there: its sender is about to notarize the same proposal itself.
4. **Backoff.** A node's backoff `b` starts at 0. Leaving a view by a timeout certificate raises it by one, to at most 4. Leaving a view by a notarization, a finalize quorum or a sync response less than `T / 2` after entering (or resuming) it lowers it by one, to at least 0. Views that keep timing out therefore wait up to 16 times longer, until the timeout exceeds what the network and the nodes actually need to notarize a view; the timeout stays there while views take more than half of it, and comes back down once they notarize well within it. A single faulty leader among honest ones still costs only `3 × slot_ms`.
5. **Tip fetching.** A validator that holds a valid proposal of the current view or a later one in its epoch (the first one signed by that view's leader) and cannot vote for it because its parent is not the node's tip asks the leader of that view, point to point, for the leader's tip: `Fetch { view }`, signed with `kind` 4. It does so when the proposal arrives, and when it enters the proposal's view holding the proposal (§5, votes), unless it has voted or timed out in that view, its signing guard forbids it to vote there (§7b), it is that leader, it holds the parent as a proposal from a view at or below its tip's (then the leader is the one behind, has nothing it lacks, and is sent this node's tip by rule 3 when its proposal's height is at most the tip's), or the parent is the zero hash; and at most once per view (it remembers the highest view it asked in). A leader proposes on its own tip, so it holds the parent's certificate. A node that receives `Fetch` drops it unless the view is in its current epoch and its signature recovers to a validator of that set whose id is the delivering peer's, and answers it exactly as a stale message from that peer (rule 3): with the tip certificate and the tip, and the entry certificate with its proposal, at most once per peer until it enters another view or its timeout fires again, a budget it shares with stale messages and with proposals at or below its tip. Rules 3 and 5 are the two directions of one exchange: a node pushes its tip to a leader that proposes behind it, and pulls the tip of a leader it is behind; neither subsumes the other, and each answer comes out of the same once-per-peer budget. The asker keeps what arrives as rule 3 says: a notarization of the parent makes the parent its tip and, its proposal held, gets its vote (§5); one for the view before the proposal's also moves it into that view. Without this, every validator that missed the votes of the leader's tip could vote only after its own view timeout made its messages stale, and validators that move through views together on timeout certificates are never stale: a leader whose tip a third or more of the stake lacked cost a full, possibly backed-off, view timeout, every time its turn came.

A node that receives `Certificate` drops it unless: its view is in the node's current epoch (§3a); its view is at or above the node's current view, or it carries a proposal; the node does not already hold that quorum together with any proposal it names; `kind` is 1, or 2 with a non-zero hash; a carried proposal hashes to `hash` and names the same view, and `hash` is non-zero; and `votes` verifies as §6 says. The count and the indices are checked before any signature is recovered, so a certificate costs at most `n` recoveries however large its message. It then keeps the proposal and the votes as if they had arrived one by one, and applies §5: a timeout certificate skips, a vote or finalize certificate notarizes (and may finalize). A block-vote certificate for a quorum the node already holds with its proposal, in a view above its tip's, is not verified again, but the node applies §5 to the quorum it holds, which changes nothing when it already did.

## 6. Certificates

A *vote certificate* is a `Certificate { kind: 2, view, hash, votes: vec<SignedVote { validator: u32, signature: [65] }> }` holding the finalize votes that finalized the block or one of its descendants. Verifying it means checking that `votes` holds at most `n` entries whose `validator` indices are distinct and index the set of `view`'s epoch, that they weigh a quorum, then that each signature recovers, over the finalize message of `(view, hash)`, to the validator its entry names. One entry that fails rejects the whole certificate. The same structure with `kind: 1` carries the block votes of a notarization, or with `hash` zero the timeout votes of a skipped view (§5a).

## 6a. Threshold certificates

Once chain state holds an active key set (15 §6.3), a validator that holds shares of it signs, with every finalize vote for a proposal that is not a suffix and whose anchor it can vouch for, the version-2 certificate message of spec 12 §7 for that proposal, `"ORANGE-FINALITY" ‖ 2 ‖ chain_id ‖ key_id ‖ height ‖ hash` with `key_id` the id of the key set active in its chain state and `hash` the proposal hash, with each of its shares through its keystore (key role 2, `SignAll`, 15 §6.4), and sends the partials in a `FinalizeShare`; the kernel deals shares in proportion to stake (15 §6.1). It can vouch for the anchor when the anchor is none, or when `anchor_height` is below the proposal's height, it has executed the block at `anchor_height`, and that block's `state_root` is `anchor_root`; otherwise its finalize vote is a plain `Finalize`. Voting and finalization never look at the anchor, so a proposal with a false anchor is finalized like any other but gets no threshold certificate while the faulty shareholders hold fewer than the threshold of shares, as validators with two thirds of the stake or less always do (15 §6.8), and a threshold certificate vouches for its proposal's anchor as for the proposal (spec 17 §4). A node that finalizes a proposal that is not a suffix gathers the partials of the finalize votes for it; when the partials of one key set that has been active (15 §6.5), of distinct shares, reach that key set's threshold, it asks its keystore to combine them, which verifies the result under that key set's group key and falls back to verifying each partial (12 §7). The 97-byte version-2 certificate (the key set's id, the proposal's height and hash, the group signature) is stored for the proposal and every ancestor it finalizes. Around a handoff (15 §6.6) shareholders whose chain states straddle it sign with different key sets, so a block or two may get no threshold certificate.

Each partial that a node receives with a finalize vote, from the shareholder its index names, is also inspected: if the node holds the proposal, the proposal anchors a height it executed with another state root, or the partial's key set was handed off at a height at or below the anchor, the partial is evidence of threshold misbehaviour (15 §5.1), which the node verifies and broadcasts in a DKG envelope for leaders to propose; of one vote's partials, the first that shows an offence is enough.

**The switch.** `FinalizeBlock.certificate` is the threshold certificate when the node stored one for the block, and the vote certificate otherwise: before the first key set is adopted, while the shareholders of the active key set online hold too few shares, for a block finalized by a suffix proposal, or when the finalize quorum carried fewer partials of one key set than its threshold (for instance because the proposal's anchor was false, or ahead of what the shareholders had executed, or because the votes straddled a handoff). The first byte and the length tell them apart (12 §7): 2 and 97 bytes for a version-2 threshold certificate, 1 and 89 bytes for a version-1 one, which this driver no longer produces, and the vote certificate otherwise. A threshold certificate verifies with `bls12381_verify` (05 §4.3) over the message rebuilt from its key id, height and hash, the tag `DST_SIG` and the group key of the key set it names.

## 7. Persistence and restart

Everything the driver keeps between steps is node-local (`persist_*`), never chain state: its `SimplexState` (view, tip, finalized height, flags, validator index, clock, sync bookkeeping, the peers answered in this view, the backoff and when the view began), the highest view it sent a `Fetch` in (§5a), proposals by hash, votes, finalize votes and partial signatures by `(view, hash)`, the notarized hash per view, the vote certificate and the threshold certificate per finalized height, the entry and tip certificates, the first hash each validator signed per kind and view, equivocation evidence (§9), messages kept for a later epoch (§3a), whether the outstanding sync request is weak (§7a), the signing guard while it lasts (§7b), its validator id, the DKG envelope pool and what it sends in each DKG phase (15 §6). The host also receives the `SimplexState` as `PersistState` after every step and hands it back at `Started`, so a restarted node resumes in the view it left with what it did there (§3); a node whose persisted tables are gone still follows from its state record. Garbage `resumed_state` is ignored and the driver starts from view 1; with no state record in its tables either, it starts under the signing guard (§7b). The host prunes the tables of heights and views consensus no longer needs when the chain state is on disk (22 §8.1); with the chain state in memory it keeps them all, since the replay below reads them.

A restarted node whose chain state is behind the finalized height its state records (a node run without the chain store of spec 22, or one whose last block's write a crash cut short) first re-executes, lowest height first and one block per step, the blocks it had finalized, from the proposals and certificates it persisted, as far as they go without a gap; the host executes and finalizes them as any other (§5), kernel switches on the way included (06 §7.6), and a replay that a restart cuts short goes on from the chain state it reached. Until its chain state reaches its view's epoch it acts as §3a says; once a block it executes, by this replay or by catch-up (§7a), brings it there, it looks itself up in that epoch's set and arms its view again (§3), its `voted` and `timed_out` flags still saying what it did there. What its tables lack it syncs (§7a). A validator that is alone, or a whole network that stops and starts, therefore comes back without a peer that holds the chain.

A restarted node whose chain state is *ahead* of the finalized height its state records (its chain store committed a block before its driver store synced, or it started from a snapshot, 22 §5 and §7) takes the heights between from the *block log*: in the step that asks for a block's execution, the driver writes the proposal, its finalize certificate and its threshold certificate, if any, under `local/log/prop/`, `local/log/cert/` and `local/log/bcert/` plus the height (node-local keys of chain state, outside the commitment, that the host commits with the block), dropping the entries 64 heights behind. On `Started` it copies those heights into its tables, makes the last one its tip when its tip is behind it, enters the view after that certificate's when its view is not past it (views only increase, §3), and sets its finalized height to the chain state's: the blocks were finalized, or they would not have been executed.

A restarted node whose tables lack the finalized head its state records has the host put that head back before `Started`, from the block log: the proposal under `prop/` and the height's `final/`, `cert/` and `bcert/` entries, as the log holds them. The host's driver store writes the state before the tables' journal, so that a restart never forgets a vote, and a crash between the two leaves exactly this: a state whose finalized height is the chain state's, and tables without that height. The driver chains every block a peer sends onto its finalized head, and without one it took none again and stayed at that height for good.

## 7a. Catch-up

A node that sees a valid proposal more than one height above its tip, a finalize quorum for a proposal it cannot connect to its finalized head, or a notarization of a view at or above its own for a proposal it lacks, sends the peer that delivered the message a `Request` with `SyncRequest { from_height: finalized + 1 }`, unless a sync request is already outstanding (an outstanding request is abandoned on entering a new view, and replaced when it was a weak request of §3a and this trigger is not). The peer answers with `Respond` carrying `SyncResponse { finalized_height, proposals, certificate, threshold }`: consecutive proposals starting at the requested height, ending at the head of the vote certificate that finalized the *top* height, `from_height + 15` or its own finalized head if lower and, with staking, never past the last block of `from_height`'s epoch; that certificate; and the threshold certificate the responder stored for the top height, or nothing. The proposals are found by following parents down from the certificate's head, which may be a suffix proposal (§3a).

The requester checks that the certificate is a finalize certificate for the last proposal and that the proposals link to its finalized head. The response is *certified* when the vote certificate verifies as §6 says against the set of its view's epoch; capping each batch at an epoch's last block guarantees the requester knows that set when it has executed everything before the batch. A full node never accepts a threshold certificate in place of the vote certificate: a threshold certificate shows that validators holding more than two thirds of the stake of its key set's epoch signed (15 §6.8), but a key set can outlive its epoch, and only the votes show that more than two thirds of the stake of the batch's own epoch finalized it. A certified response is executed and finalized under its vote certificate, and `threshold` is kept as the blocks' threshold certificate when it is a version-2 certificate for the last proposal `P` (not a suffix) that verifies under the group key of the key set it names, and that key set was in force for `P` by the requester's chain state before the batch: it was made active at a height below `P`'s, and not handed off at a height at or below `P`'s anchor (15 §6.5). That is the key an honest shareholder signs `P` with, found by following the chain's handoffs; a batch whose handoff the requester has not executed yet keeps no threshold certificate, which costs it nothing but the artifact. Only a vote certificate whose view is in the requester's current epoch moves it: the head becomes its tip if the certificate's view is above the tip's (a tip from a later view already extends the head), and the node enters the view after the certificate's if it is not past it, with the certificate as its entry certificate. It asks again while the responder reported a higher finalized height. Anything that fails a check is dropped. The host keeps a request on the wire across the views the driver enters meanwhile, and hands its answer to the driver's next request for the same blocks (09 §6a), so an answer slower than a view is not lost.

On `Started`, the driver lowers its finalized height to the height of the chain state, so a node that kept its driver record but lost its chain state syncs instead of executing on the wrong parent.

## 7b. Lost signing records

A validator's *signing record* is its state record: the `SimplexState` in its tables or handed back as `resumed_state` (§7), whose view and flags are what keep it from signing twice in one view (§3). A node that starts with neither, from a new or wiped data directory, from a reinstall with its key alone, or from a snapshot (22 §7), cannot know what its key signed before: replaying the chain it would enter view 1 and the first view of every epoch again, and as leader propose in each, and once caught up it could sign in the views it was in just before it lost its record. Catching up is verification only; signing waits until the node has seen the network sign past every view its lost record can have covered. It starts under the *signing guard*, persisted in its tables as `SigningGuard { witnessed: u64, live: vec<LiveSigner { view: u64, validator: u32 }> }` under `simplex/guard`, an empty value once the guard ends, so that a guarded node that restarts with its tables is still guarded. A node at chain height 0 whose own stake alone is a quorum of the genesis set (a chain of one validator, `orange dev`) is not guarded: no quorum it could witness need include anyone but itself, so the guard could bound nothing. Past height 0 (it started from a snapshot, or its chain state outlived its tables) a node without a record is always guarded, whatever its stake: the set it can judge its stake by when it starts, the set of the epoch of the block log's last certificate (§7), need not be the set of the epoch it signs in, and a validator that held more than two thirds of an earlier set's stake, as the first validator of a single-operator bootstrap does, would otherwise sign unguarded in views it signed in before, be slashed for it, and with its stake a quorum of that epoch finalize alone a second block at one of its heights. A guarded node whose own stake is a quorum of its current set witnesses its own timeout votes, and signs again two views later.

1. **What a guarded node signs.** It verifies, executes, finalizes, syncs and forwards certificates as any node does (§5, §5a, §7a), and it signs timeout votes, in any view: they all carry the zero hash, are never evidence (§9), and keep views moving and draw the certificates of §5a. It signs no proposal, block vote, finalize vote (nor the partial signatures that go with one, §6a) or `Fetch` in a view the guard covers (rule 3). Until it has witnessed a view it sends no DKG envelope (15 §6.3), nor does any node whose chain state is behind its view's epoch (§3a): both are catching up.
2. **Witnessing.** A *live signer* of view `w` is a validator whose proposal, block vote or timeout vote of `w` the node verifies, delivered by that validator itself (the delivering peer's id, proved in its handshake, 09 §3, is the signer's id), or the node itself for its own timeout votes, with `w` at or above the node's current view and in its current epoch. The guard keeps the live signers of the views at or above the current one, at most 256, those of the lowest views. The first view whose live signers weigh a quorum of its epoch's set is the guard's *witnessed* view `W`, fixed once and the live signers forgotten. At chain height 0 a guarded validator times view 1 out as soon as it starts (sets `timed_out` and broadcasts the timeout vote of view 1), so that on a new chain, where every validator starts guarded, the timeout votes of view 1 are witnessed at once; when the witnessed view is 1 and the node has executed nothing, the guard ends there.
3. **Signing again.** With `W` witnessed, the guard covers the views up to `W + 1` and, with staking, `first_view(epoch(W) + 1)`: the node signs there nothing but timeout votes, and elsewhere as any node. The guard ends when the node arms a view past all of them.

Why `W + 1` and the next epoch's first view. An honest validator signs proposals, block votes and timeout votes only in its current view and finalize votes for the view before it; its view only increases; and it enters a view `V > 1` only holding a quorum certificate of view `V − 1` (§5) or, when `V` is `first_view(e)`, after executing `end(e − 1)`, which a finalize quorum of a view of epoch `e − 1` finalized (§3a). Let `V` be the view the lost record was in when it was lost, and `Q` the quorum that brought it there, signed before. The live signers of `W` signed after the node started: a peer's message reaches it only over a connection made after it started (a message goes to the peers handshaken when it is sent, 09 §4, and no node relays another's consensus messages), and an honest validator broadcasts proposals, block votes and timeout votes only for its current view. `Q` and the live signers of `W` each weigh more than two thirds of the stake, so they share more than a third; while Byzantine validators and validators that lost their records together hold less than a third, they share an honest validator with its record, which signed in `Q` and later in `W`, so `W` is at least `Q`'s view. If `Q` certified `V − 1`, then `V ≤ W + 1`. If `Q` finalized `end(e − 1)` in a view of epoch `e − 1` and `V = first_view(e)`, then either `epoch(W) ≥ e` and `V ≤ W`, or `epoch(W) = e − 1` and `V = first_view(epoch(W) + 1)`. The record's earlier views are below `V`, and those of `epoch(W)` or earlier are at most `W + 1` by the same argument for the quorum that brought it into each. So every view the lost record can have signed in is at most `W + 1` or is `first_view(epoch(W) + 1)`, and the guard covers exactly those. At chain height 0 a witnessed view 1 means the quorum `Q`, if there was one, certified view 1 at most, so the lost record covered views 1 and 2 at most; the guard ending there leaves the one case of the limits below.

The guard's timeout votes are safe for agreement under the same bound: a validator that forgot its finalize vote in a view `w` and times out in `w` has done both, and a finalize quorum and a timeout quorum for `w` need more than a third of the stake to do both (§8). They also keep the chain live when guarded validators hold a third of the stake or more: their timeout votes count as live signers and move every view, so the guarded ones witness a view and sign again two views later, although agreement is then no longer guaranteed.

Limits. The guard protects a validator whose record is gone, not one whose key runs twice: two live copies of one key both sign, and are slashed (15 §5). It assumes that Byzantine validators and validators under the guard together hold less than a third of the stake of the epoch. A validator that lost its record while its chain was in view 2 and a quorum still signed in view 1 can sign view 2 again; a node with nothing executed that witnesses view 1 cannot tell that from a new chain. Nor can a node that lost its record and its chain state at once and whose own stake is a quorum of the genesis set: it starts unguarded, as on a new chain, and signs again in the views of epoch 0. The operator of such a validator keeps its data directory, or brings it back from a snapshot, which starts it past height 0 and under the guard.

## 8. Properties and limits of this version

- Safety: two conflicting proposals cannot both be notarized in one view (each honest validator votes at most once per view, across restarts), and a finalized proposal is on every later honest tip. A validator that finalized `B` in view `w` had `B` as its tip and only moves its tip to proposals notarized in later views, so it votes only for descendants of `B`; those are at least `q − f` validators, which leaves at most `f + n − q < q` votes for anything conflicting, however other validators jumped between views. A validator that timed out in `w` never finalizes `w`, and a finalize quorum and a timeout quorum for one view cannot both exist. A validator that lost its signing record counts as faulty in these bounds until its signing guard ends (§7b).
- Liveness: after the network delivers within `slot_ms`, every honest validator reaches the highest view any honest validator is in within one view timeout plus two message delays (by forwarding or by quorums of repeated timeout votes); from then on, a view with an honest leader finalizes within about two message delays after the proposal when the others hold its tip, and within about four when some of them lack it and fetch it (§5a), and a faulty leader costs one view timeout, `3 × slot_ms` when the views before it notarized, also when it proposes a timestamp as far ahead as `MAX_DRIFT_MS` allows (§5); so does a leader that proposes behind the others' tip, which is sent that tip (§5a, rule 3) and proposes on it the next time it leads. When messages and processing take longer than the base timeout, backoff (§5a) lengthens the timeout until views notarize, up to `48 × slot_ms`; a network slower than that is not live.
- Finality for a block proposed in view `v` arrives in view `v` or `v + 1`; `latest`, `safe` and `finalized` coincide for RPC.
- Epoch changes: the validators of epoch `e` decide everything until `end(e)` is finalized and executed; a validator that leaves at an epoch boundary must stay online until then, and a shareholder until the handoff of its key set is recorded (15 §6.6). Nodes enter a new epoch at slightly different times; one that has not yet executed `end(e)` keeps the new epoch's messages and takes them up once it has.
- Not in this version: asynchronous execution with lag `k`, transaction re-admission after a proposal that was not notarized, a sync response sized to the frame (one of 16 proposals near `MAX_PROPOSAL_BYTES`, or of 16 honest blocks full of transactions, is longer than a frame of 09 §2, which closes the connection it goes out on), and a bound on the votes and evidence a validator can make others store by signing messages for views far ahead. Certificate forwarding (§5a) amplifies: a stale vote of about 106 bytes, or a `Fetch` of 74, or a proposal at or below the receiver's tip, can draw two certificates and a proposal of up to a block's size, once per validator per view and timeout period (all three share the budget). The budget is kept per peer id, and a peer's id is proved in the handshake (09 §3), so no peer can claim a validator's id to draw the answers meant for it or use up that validator's budget.

## 9. Equivocation evidence

An honest validator signs at most one hash per kind and view: one proposal (as leader), one block vote, one finalize vote. Timeout votes all carry the zero hash and never conflict, and a timeout vote beside a block vote in the same view is allowed (§5).

**Detection.** For every proposal, block vote and finalize vote whose signature it verifies, including each vote of a `Certificate` or of a sync response's certificate (§7a) that verifies, even when the certificate as a whole is then dropped, a node records the first hash the signer signed for that kind and view. A second, different hash is an equivocation. The node keeps both signed messages node-locally as

```
struct SignedHash { hash: [32], signature: [65] }
struct Evidence   { kind: u8, view: u64, validator: u32, first: SignedHash, second: SignedHash }   // first.hash < second.hash
```

in its *pending evidence*, emits `Metric { name: "equivocations", value: 1 }`, and emits `PeerScore { peer, delta: −100 }` for the peer that delivered the second message, when the record can still punish someone: chain state does not hold its offence (validator, view, kind), its *offender* (the validator its index names in the set of the epoch of its view) is not jailed (15 §5), and no pending record names the same offender. Otherwise the equivocation is dropped, and nothing is emitted. An offender is punished once whatever else it signs (15 §5), so one record against it is all the chain needs: a validator, current or former, that signs conflicting messages for many views, relayed by other peers, whom the budget of §5a does not cover, holds one place in the pending list, never ahead of the evidence against others, and the list holds at most one record per validator.

**Recording.** A leader puts up to 8 pending records into its proposal's `evidence`, oldest first; a record leaves the pending list once chain state holds its offence or its offender is jailed, by that offence or any other, and without staking a later offence of the same validator may then take its place. Executing a block, before its transactions, decodes `Block.participation` as `Participation { evidence: vec<Evidence>, dkg: vec<bytes> }` and takes at most 8 records. A record is kept when it is well formed (`kind` ≤ 2, `first.hash < second.hash`, and for `kind` 1 `first.hash` non-zero), `validator` indexes the set of the epoch of `view`, both signatures recover to that validator over the messages of `(kind, view, hash)`, and its offence is not yet on record. Kept records are stored in chain state:

| Key | Value |
|---|---|
| `evidence/` + index (big-endian u64) | `Evidence`, indices from 0 in the order recorded |
| `meta/evidence_count` | `u64`, the number of records |
| `evseen/` + validator (big-endian u32) ‖ view (big-endian u64) ‖ kind | `u64` index of the record for that offence |

Anything else in `participation` is ignored, so evidence never makes a block invalid. The query `evidence` takes a `u64` first index and returns `vec<Evidence>`: the records from that index on, at most 64.

**Slashing hook.** Recording a record is the point where the offender's stake is cut, in the same state transition and therefore identically on every node: with staking, spec 15 §5 slashes the offender once and removes it from the next set. Without staking, recording is all that happens.

**Threshold misbehaviour.** Partials of the threshold key signed against the rules of §6a and 15 §6.6 are evidence too. They travel in DKG envelopes rather than in `evidence`, and spec 15 §5.1–§5.2 says how they are found, recorded and slashed; an offender is punished once whichever kind of offence is recorded first.
