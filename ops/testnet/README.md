# Running a public testnet

This is the runbook for a Solo network whose validators are run by several operators on their own hosts, one node per host. Everything here was rehearsed on one machine (`tools/rehearse-testnet.sh`, below); no server, cloud account or DNS name is assumed to exist yet.

The pieces:

| File | What it is |
|---|---|
| `solo key generate`, `solo genesis operator\|assemble\|hash\|verify` | the genesis ceremony (`crates/solo-cli/src/ceremony.rs`) |
| `genesis-template.json` | the coordinator's starting point: name `tangerine`, real epoch lengths, fee market at its defaults |
| `solo-host` | everything that happens on one host: run, start, stop, health, install and roll back the binary, logs, key backups, resource use |
| `solo-ops` | the control side: reads an inventory, copies files over ssh and calls `solo-host`; `--dry-run` prints every command instead |
| `inventory.example` | the inventory format |
| `solo-node.service` | the systemd unit (restart policy, limits, hardening) |
| `compose.node.yml` | the container alternative, from the image `ops/Dockerfile` builds |
| `../networks.json` | the registry of launched networks: name, kind, chain id, genesis hash, launch date |
| `../alerts.yml`, `../grafana-solo.json` | the alert rules and dashboard; `solo-ops prometheus` writes the scrape configuration |

## 1. What a validator is made of

A validator has one secret: its **consensus key** (secp256k1). Everything else is derived from it or produced on chain:

- the validator id (spec 08 §2) is `keccak256` of its public key, and its account (signals, governance votes, fees) the id's last 20 bytes;
- its node key on the transport is the same key (spec 09 §3), so peers authenticate it as the validator;
- the encryption key its DKG shares are dealt to (48 bytes, spec 15 §2) is derived from it;
- the threshold BLS key is generated by the validators' first DKG on chain and replaced every epoch (spec 15 §6); no BLS secret exists before the chain runs, and each node keeps its share in its data directory.

An observer (an RPC node, a bootnode) has no consensus key. Give it a lasting **node key** (`solo node --node-key-file`) so that it advertises a signed address record and its peers' persisted tables keep it across restarts; without one it dials with a fresh key at every start and advertises nothing.

## 2. The genesis ceremony

Roles: **operators** (one per validator) and one **coordinator**, who may also be an operator. Only public material moves between them.

1. **Each operator, on their own machine** (offline is fine):

   ```sh
   solo key generate --out validator.key           # mode 0600; refuses to overwrite
   solo genesis operator --key-file validator.key --name op-a --chain-id <id> \
       --p2p <public ip>:30333 --out op-a.json      # the card: id, account, DKG key, bootnode address, signature
   ```

   Back `validator.key` up offline now (two copies, encrypted). Send only `op-a.json` to the coordinator. `--p2p` is optional; with it the node is listed as a bootnode.

2. **The coordinator** copies `genesis-template.json` and sets `chainId` (unique: check chainlist.org and `../networks.json`), `timestamp` (the launch time, Unix seconds, in the future: no block is made before it, so every operator can start early and the chain begins on time), `governance` (the coordinator's governance account, `solo key generate` then `solo key --key-file` prints its `address`) and anything else, then:

   ```sh
   solo genesis assemble --template template.json --kernel kernel.elf \
       --operator op-a.json --operator op-b.json ... --out genesis.json
   # genesis of chain <id> with <n> validators written to genesis.json
   # genesis hash 0x…
   ```

   `assemble` checks every card's signature (it must recover to the validator it names and be made for this chain id), sorts the validators, lists their DKG keys under `staking.keys`, funds each validator's account (1 000 ether by default, `--operator-funding`) unless the template does, writes `bootnodes` (the template's, the cards' `--p2p`, any `--bootnode`) and runs the genesis through the kernel's `kernel_init`. The output does not depend on the order of the cards: anyone with the template and the cards assembles the same file.

3. **Publish** `genesis.json`, the genesis hash, `kernel.elf` (with its `sha256sum`), the template and every card, in one place every operator reads (a git repository is fine), and add the network to `../networks.json` with kind `testnet`.

4. **Each operator verifies** before starting anything:

   ```sh
   solo genesis verify --genesis genesis.json --kernel kernel.elf --hash 0x<published> \
       --key-file validator.key [--operator op-b.json ...]
   ```

   It recomputes the genesis hash under the kernel, checks the operator's own validator is in the set with the DKG key its key derives (a wrong DKG key would leave that validator without a share), checks any cards given, and prints the parameters for a human to read: name, chain id, genesis time, slot, epochs, governance, fees, bootnodes. The genesis hash covers every chain parameter, the name included (spec 20 §3.4); it does not cover `bootnodes`, which are only first addresses to dial: a peer of another chain fails the handshake (spec 09 §3).

## 3. What to provision per host

One node per host. Roles:

| Role | Runs | Ports open to the internet | Notes |
|---|---|---|---|
| `validator` | consensus key, `--serve-snapshots` | p2p (30333/tcp) | RPC on the private interface only |
| `rpc` | observer with a node key, larger `--state-history` or `--archive` | p2p, and the RPC through a reverse proxy | `public-rpc=1` adds `--no-rpc-stop` |
| `bootnode` | observer with a node key | p2p | small; any operator can run one |

Measured on the rehearsal (section 8): a node at the rehearsal's load uses under a tenth of a core, 130 to 240 MiB of memory, about 9 KB/s of p2p traffic at one block a second, and its data grows by 10 to 30 KB a block. A testnet host that leaves room for load spikes, snapshot exports and months of growth:

| | validator | rpc | bootnode |
|---|---|---|---|
| CPU | 2 dedicated vCPU | 4 vCPU | 1–2 vCPU |
| RAM | 4 GiB | 8 GiB | 2 GiB |
| Disk | 100 GiB SSD (NVMe preferred) | 200 GiB SSD, more for `--archive` | 50 GiB |
| Network | any 1 Gbit/s port; about 25 GB a month at four validators (section 8) | the same plus RPC traffic | the same |

Disk grows with state and with the snapshots a serving node keeps (two epochs' worth, spec 22 §7.4); watch `solo_store_size_bytes`. Time must be synchronized (chrony or systemd-timesyncd): block timestamps and the genesis time are wall-clock.

## 4. Layout on a host

```
/opt/solo/bin/solo -> solo-<sha256 prefix>   the binary; solo.previous is the one before
/opt/solo/bin/solo-host                       the host script
/etc/solo/node.env                            the node's configuration (solo-ops renders it)
/etc/solo/genesis.json, kernel.elf            the published genesis and genesis kernel
/etc/solo/keys/validator.key | node.key       mode 0600, owner root, group solo
/var/lib/solo/                                the data directory (solo user, 0700):
    driver.state, persist.log                 the driver's state: never two copies of it alive
    chain.redb                                the chain store (spec 22)
    peers.records                             the persisted peer table (spec 09 §5a.7)
    snapshots/                                snapshots served to joining nodes
```

`node.env` (rendered from the inventory; every variable is documented at the top of `solo-host`):

```sh
SOLO_NAME=val-a
SOLO_ROLE=validator
SOLO_LISTEN=192.0.2.10:30333          # bind
SOLO_ADVERTISE=192.0.2.10:30333       # signed into the peer record
SOLO_RPC=10.0.0.10:8545               # JSON-RPC, /metrics, /status, /health: private
SOLO_BOOTSTRAP="192.0.2.20:30333"     # the inventory's bootnodes, beyond the genesis bootnodes
SOLO_GENESIS_HASH=0x…                 # check-config refuses another genesis
SOLO_SERVE_SNAPSHOTS=1
SOLO_JOIN=sync                        # only on a node that joins late, see section 6
SOLO_TRUST_FROM=10.0.0.10:8545,10.0.0.11:8545
```

**Ports and firewall.** Open p2p (tcp) to the world. Bind the RPC to a private interface (a provider VPC, or WireGuard between the operator's hosts and their monitoring) and firewall it to those addresses: it serves `solo_stop`, `/metrics` and the mempool, and every request runs on the node's consensus thread under a gas budget. A public RPC endpoint goes through a reverse proxy (TLS, rate limits, request size limits) to an `rpc`-role node started with `public-rpc=1`, which refuses `solo_stop`; never expose a validator's RPC. Prometheus scrapes the RPC address, so it sits on the same private network.

**Bootnodes and the peer table.** A node dials its `--peer`s, its `--bootstrap` addresses and the genesis `bootnodes`, learns the rest by peer exchange (spec 09 §5a), and keeps the peers that answered in `peers.records`, which it takes up again at start (entries seen in the last 7 days). So a restarted node finds the network even if every bootnode is down; a brand-new node needs at least one reachable bootnode or peer. Keep two or more bootnodes run by different operators, listed in the genesis.

**Logs.** Under systemd the node logs to journald (`SyslogIdentifier=solo-node`); cap it with `SystemMaxUse=2G` in `/etc/systemd/journald.conf`. In the container, the json-file driver rotates at 5 × 50 MB. `solo-ops logs <host>` and `solo-ops collect-logs <dir>` read either.

**Key backups.** `solo-ops backup-keys <dir>` pulls a tar of each host's key directory (mode 0600) to move offline. Never run one consensus key on two hosts at once: both would vote, which is equivocation, and the chain slashes it (spec 15). A validator restored on a new host from its key alone, without its old `driver.state` and `persist.log`, may vote again in a view it voted in; restore only after the old host is certainly dead and a view has passed (spec 22 §7.3), or move the whole data directory with the key.

## 5. Deploy

From the operator's machine, with an inventory of their own hosts (`inventory.example`):

```sh
cd ops/testnet
./solo-ops --inventory inv hosts                                   # what it parsed
./solo-ops --inventory inv --dry-run install --binary ../../target/release/solo   # print, run nothing
./solo-ops --inventory inv install --binary ../../target/release/solo
./solo-ops --inventory inv configure --network <dir with genesis.json, kernel.elf, genesis.hash>
./solo-ops --inventory inv start
./solo-ops --inventory inv wait-healthy 600
```

`install` creates the `solo` user and directories, installs `solo-node.service`, `solo-host` and the binary (as `solo-<hash>`, the previous one kept). `configure` pushes the genesis, the kernel, the rendered `node.env` and each host's key from `key=`, then runs `solo-host check-config` there: files present, key mode 0600, and the genesis hash the kernel computes on that host equal to the published one. The systemd unit runs `check-config` before every start as well.

The container instead of systemd: build or load the image (`docker build -f ops/Dockerfile -t solo:<release> .`), install `solo-host` and `/etc/solo` as above, and run `SOLO_IMAGE=solo:<release> docker compose -f compose.node.yml up -d` on the host. It runs the same `solo-host run` with host networking, `/etc/solo` read-only and `/var/lib/solo` as the data directory.

`solo-ops` is plain shell over ssh (`SOLO_OPS_SSH`, `SOLO_OPS_SCP`, `SOLO_OPS_SUDO` change how). All host-side logic is in `solo-host`, so an Ansible playbook only has to copy the same files and call `solo-host`; `solo-ops ansible-inventory` prints the inventory in Ansible's format.

## 6. Verify and operate

```sh
./solo-ops --inventory inv health          # solo doctor on every host, then agreement on a finalized block
./solo-ops --inventory inv status          # running or not, and /status
./solo-ops --inventory inv resources       # pid, RSS, CPU time, data size, p2p bytes in/out
solo devnet status --rpc 10.0.0.10:8545,10.0.0.11:8545     # one line per node
solo devnet wait --rpc <all rpcs> --caught-up --no-equivocations
```

`health` passes when every host's `solo doctor` passes (head advancing, finality close behind, peers, mempool, kernel calls within bounds: spec 11 §7, the same thresholds as `alerts.yml`) and every host has the same hash at the lowest finalized height among them.

**A node joining later** (a new RPC node, a replaced host) starts from a snapshot its peers serve instead of replaying the chain: give it `join=sync` and `trust=<rpc,...>` in the inventory, naming nodes the operator trusts. On its first start, with an empty data directory, `solo-host` asks those nodes for the chain's current group key (`solo snapshot trust-key`, which fails unless they all report the same key), and the node fetches and verifies the snapshot under it (`--sync-from-peers --trust-key`, spec 22 §7.4), then syncs the blocks after it. Once it holds a chain it starts normally. If the key rotates between asking and fetching, the sync fails and the node exits; systemd starts it again and it asks again.

**Rolling restart and binary upgrades.**

```sh
./solo-ops --inventory inv rolling-restart                         # one host at a time
./solo-ops --inventory inv upgrade-binary --binary <new solo>      # install everywhere, then roll
./solo-ops --inventory inv rollback                                # previous binary everywhere, then roll
```

Each host is restarted and must be healthy and finalized as far as the others were before the next one goes. A restarted validator resumes the view it left from its driver state and never votes twice in it (spec 08 §7). Operators coordinate so that no more than one validator of the network restarts at a time: below a quorum of stake the chain stops finalizing until they return.

## 7. Kernel upgrades and governance

A kernel upgrade switches every node at the same block (spec 13 §4). Before proposing one, check that every operator's host release supports the gates the new kernel needs (`solo_upgradeStatus`, `/status` `missingGates`), and upgrade the binary first if not.

**Key track** (the template's default for a testnet's first days: the coordinator's governance key acts alone):

```sh
solo upgrade --rpc 10.0.0.10:8545 --key-file governance.key --kernel kernel_v2.elf   # stage, propose, wait for the receipts
solo devnet wait --rpc <all rpcs> --kernel-version 2 --timeout 3600
```

`solo upgrade` stages the module in chunks, proposes an activation height `upgradeDelay` blocks ahead, and resends with more slack if the proposal lands too late. Announce the activation height to every operator; each watches `/status` `pendingUpgrade` and, after the height, `kernelVersion`.

**Stake track** (validators decide; switch once the network is stable: `solo gov set-mode stake`, after `solo gov set-params <votingBlocks> <timelockBlocks> <quorumBps> <deposit>`, both sent by the governance key). Each step is calldata `solo gov` prints, sent with any wallet or `cast send` to the governance address `0x0000000000000000000000000000000000005010`:

1. Any validator stages the module from its account (staging is not a governance action; spec 13 §2.2). Under the stake track that is the validator's consensus key; to keep that key off a laptop, the operator runs `cast send` on the validator host itself, or the network keeps the key track until a dedicated proposer flow exists.
2. A validator submits the proposal: `solo gov submit 0x…5010 <propose calldata>` (the `propose(bytes32 codeHash, uint64 activationHeight, uint64 requiredGates)` action, spec 13 §3), choosing an activation height past the end of the voting period plus the timelock plus `upgradeDelay`.
3. Every operator checks the proposal (`solo_getProposal <id>`: target, data, the code hash of the staged module against the published kernel's) and votes: `solo gov vote <id> yes`.
4. After the voting period and the timelock anyone executes it: `solo gov execute <id>`. The guardian can veto during the timelock; a majority of stake can stop it on the fast track (`solo gov submit 0x…5010 <cancel calldata>`).
5. Every operator verifies the switch: `solo devnet wait --rpc <their rpcs> --kernel-version <v>`, and `solo devnet status` shows the same kernel hash everywhere.

## 8. The rehearsal, and what it measured

```sh
tools/rehearse-testnet.sh            # SOLO_BIN, VALIDATORS, SLOT_MS, EPOCH_BLOCKS change it; KEEP=1 keeps the directory
```

It runs the whole flow on one machine, each host a directory under the work directory with its own loopback ports and `ssh` replaced by `local` in the inventory: the ceremony with four operator directories (keys never leave them, only the cards do), genesis assembly and verification by every operator plus a tampered copy that fails, `solo-ops install` and `configure` on six hosts (with a dry run of the same over ssh), four validators and an RPC node started and healthy, a late joiner that fetches a snapshot from its peers and catches up, a kernel upgrade by the governance key that every node takes, a rolling restart of all six, health, agreement and no equivocation, resource use, and teardown. It prints a PASS line per phase.

**Result (2026-11-04, Apple M4 Pro, 12 cores, 24 GiB, the release build, all six nodes and the load on the one machine):** every phase passed, in about 16 minutes with a 900 s steady state (`SOAK=900`) and in about 3 minutes with the default 120 s. The late joiner fetched the epoch-1 snapshot (block 80, 328 entries, threshold certificate) and caught up in 1 to 2 s; the kernel upgrade activated on all six nodes; the rolling restart took each host down and back with no equivocation. The steady state, 900 s after the rolling restart, 1 659 blocks at 400 ms slots under about 0.8 value transfers a second:

| val-0 | 237 | 8.5 | 6 543 | 9 767 | 3 549 | 5 298 | 192 224 |
| val-1 | 227 | 7.8 | 6 873 | 10 682 | 3 729 | 5 795 | 191 904 |
| val-2 | 189 | 7.8 | 6 173 | 11 284 | 3 348 | 6 121 | 189 920 |

At the end each data directory held about 45 MB of `chain.redb`, 9 MB of `persist.log` and 10 MB of snapshots, after about 1 800 blocks.

What it means for a testnet at the template's 1 s slots, four validators:

- **Bandwidth**: about 9 KB per block in and out together for a validator, so about 9 KB/s, 0.8 GB a day, 25 GB a month. Consensus traffic grows with the validator count (every validator's votes reach every other), so seven validators carry roughly 1.75 times that. An observer mostly receives. RPC traffic comes on top and depends on users.
- **CPU**: well under a tenth of a core at this load. Block execution, DKG rounds at epoch boundaries and snapshot exports are the spikes; 2 vCPU leaves room.
- **Memory**: 130 to 240 MiB after 1 800 blocks. Before the fix below the same run reached 350 MiB on every node and grew without bound. It still rises with the chain store's page cache (redb's default cache allows up to 1 GiB), so plan 4 GiB, and confirm the plateau in a soak of days before mainnet.
- **Disk**: the first 1 800 blocks wrote about 29 KB a block, while the 1 024-block history window, the driver's tables and the snapshots fill; past the window a single node with empty blocks still grew by about 10 KB a block (the block log and the store's free pages), which at 1 s slots is under 1 GB a day. Size disks for months, not days (section 3), watch `solo_store_size_bytes`, and measure it again in a long soak.

**Bugs the rehearsal found, fixed with regression tests:**

- *Memory grew with every step.* `Node::metrics` kept every metric the driver ever emitted, a few hundred entries per block, and nothing in a running node reads it (the telemetry holds the values). A `solo dev` node at 50 ms slots grew from 58 MiB to 132 MiB over 5 600 blocks; it now keeps the latest 16 384 to 32 768 emissions (`METRIC_HISTORY`), and the same probe stays between 44 and 61 MiB (`crates/solo-node/tests/chain.rs`).
- *The peer count counted connections.* Two nodes that both dial each other hold two connections (spec 09 §5), and `ethereum_peer_count`, `/status` `peers` and `solo doctor --min-peers` counted both: a node of a six-node network reported 10 peers, and a node with fewer distinct peers than the count passed `solo devnet wait --peers` and the compose smoke test's peer check. It now counts each peer once (`crates/solo-node/tests/net.rs`, `a_peer_connected_twice_counts_once`; spec 11 §4).
- *A joining node had no way to learn what to trust.* `--sync-from-peers` on a staking chain needs the current group key, which no RPC method served: `solo_getGroupKey` (spec 17 §7) and `solo snapshot trust-key` now do.
- *A public RPC node could be stopped by anyone*, through the unauthenticated `solo_stop`: `--no-rpc-stop` refuses it.

## 9. Incidents

**A validator is down.** The others keep finalizing as long as more than two thirds of the stake is up (spec 08). `solo-ops status`, `solo-ops logs <host> 500`; fix and `solo-ops --hosts <host> start`. It resumes from its driver state and syncs the blocks it missed (spec 08 §7a). If the host is lost, see "a key compromise or a lost host" below before running the key anywhere else. A validator that stays down misses its DKG phases and holds no share of the next key; it rejoins the threshold key at the next epoch after it returns.

**The chain stalls** (head age and finality lag alerts on every node). Usually more than a third of the stake is offline or partitioned. `solo devnet status --rpc <all>`: which nodes are up, their heads and peers. Bring validators back; check clocks (`timedatectl`), firewalls on the p2p port, and that peers find each other (`peers` in `/status`; `peers.records` on disk). Nodes resume on their own once a quorum is back; nothing needs resetting. A stall right at an upgrade's activation height with `upgradeAlert` set means hosts that cannot run the new kernel: upgrade the binary on those hosts.

**A key compromise or a lost host.** Stop the node holding the key if it still runs (`solo-ops --hosts <host> stop`, or cut the host off). The key's stake is at risk of being slashed if anyone signs twice with it, so never start a second copy while the first may still run. Unbond the validator (`unbond` at the staking address, spec 15) and, for a new key, register a new validator with a new card; under the key track the coordinator can also act through governance. A compromised observer node key only lets someone impersonate that observer: generate a new one and restart.

**A bad binary.** `solo-ops rollback` puts the previous binary back everywhere with a rolling restart.

## 10. What the owner decides

The tooling is ready; these are decisions, with no price quoted here that has not been checked with a provider:

- **How many hosts**: validators (four is the least for a network that survives one down; seven tolerates two), at least two bootnodes, one or more RPC nodes, and one monitoring host (Prometheus, Grafana, an alert receiver).
- **Who operates them**: one operator running every validator (simplest, not decentralized) or several, each with their own hosts and keys.
- **Provider and regions**: one provider and region (lowest latency, a shared failure) or several (resilience, more latency per round); sizes from section 3.
- **The chain id** (unique, checked against chainlist.org), the genesis time, the slot length and epoch length (the template's 1 s slots and 3 600-block epochs, one hour), and the governance track and key holder.
- **A public RPC endpoint**: domain, TLS, reverse proxy and rate limits; and where `../networks.json` and the published genesis live.
- **Monitoring and alerting**: where Prometheus runs, where alerts go (email, chat, a pager), who is on call.
- **The monthly budget**, once the above is chosen and priced with the provider.
